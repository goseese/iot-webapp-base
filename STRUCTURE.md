# Voltastc source map

One line per folder. The architecture the code follows is the iot-platform skill; settled
deviations for this app are in DECISIONS.md.

- `app.js` boot: HTTP listens first (web and all roles), then database, migrations and seeds (ingest and all roles only), settings, the realtime feed (web) and ingest plus jobs (ingest, through `services/leader.js`). `/health` reports build, host, pid and whether this process runs ingest. `ecosystem.config.js` runs one `web` and one `ingest` process under pm2.
- `config/` env (typed `.env`), settings cache with env override, secret encryption and `siteName()`, logger, build identity.
- `db/` knex instance on pg (`T()` is a pass through, `insertId()` normalises inserts, `isUniqueViolation()` catches 23505, RDS SSL verified with `DB_SSL_CA`), migrations runner (advisory lock, one transaction per file), database creation, shadow sync of device types, repos (thin SQL per table; `credentials.js` is the one place to find a unit's broker identity, by MAC or GUID, and a unit's current placement; `events.js` writes and reads the event log and feeds its live view).
- `migrations/` forward-only PostgreSQL files (`0001_baseline.sql` the original schema, closed; `0002_event_log.sql` onward: 0002 event log, 0003 support requests (replaced by 0010), 0004 pod stations, 0005 command queue, 0006 athletes and wristbands, 0007 OTA progress, 0008 support page and 0009 support columns (both replaced by 0010), 0010 support requests rebuilt, 0011 alarm titles: title columns, `notifications.subject` 255, audit_log type and time index, 0012 MFA sign in codes: `users.mfa_mode` and `users.mfa_channel`), applied by the ingest process at boot or `scripts/migrate.js`.
- `seeds/` idempotent: site settings (grouped, driver-declared), known lists, superadmin, System account, platform server device, default alert groups.
- `permissions.js`, `metrics/`, `deviceTypes/`, `reportTypes/`: code-owned declarations the database shadows. A device type module also declares its `models` (what provisioning accepts), the gateway `configKeys` (Config tab) and `commands` (Commands tab). Types: `platform_server` and the pods (`controller_pod`, `account_pod`, `target_accel`, `target_tof`); `deviceTypes/shared/` holds pieces they share (a subfolder, because every top level file is loaded as a type).
- `mqtt/` topic table (`topics.js`, the only place topics live, and the per device ACLs), broker settings (`broker.js`, from site settings; `watch.js` reconnects within 15 s when they change), the ingest client (fixed `MQTT_CLIENT_ID`, ingest process only) and `downlink.js` (server to device publishes through whichever connection the process has, never retained).
- `pipeline/` stage 1 (identify: topics, unit and placement lookup, registry, coverage, dedup, where unplaced MACs are heard) then stages 2..6 in index.js (insert, hooks, signals, alarms, publish); `levels.js` adds battery and signal percent before insert.
- `services/` business logic: leader (single server stub: the ingest process runs ingest and jobs), alarms (ladder, engine, notify, nodata, escalation, actions, armed, title: the alarm title resolver and the title field model, ruleLog and ruleHistory: the alarm rule change log written and read back), mail (`none`, `ses`) and sms drivers (kept, hidden in the UI), broker drivers (static and dynsec, chosen by the `BROKER_DRIVER` setting), provisioning, connectEndpoint (retained con/endpoint message), activity (handler events into the event log, login lockout), mfa (sign in codes: who needs one including the `.env` override, making and checking codes, the send with SMS falling back to email, begin, resend and check; `SMS_VISIBLE` keeps SMS hidden), unitConfig and configValues (gateway config: reported values, pending writes, re-send on connect), levels (battery chemistry and radio signal percent tables), devices (also `createSensor`, sensors are created on first value) and deviceFlows, grants, invites, reports, webhooks, apiHelpers (pure helpers for `routes/api.js`: severity order, epoch paging, limits, typed audit values), apiDocs (the one source of the API and webhook docs: both docs tabs and the Download docs Markdown file), display, visibility, unclaimed (unclaimed devices per account: list, ignore, claim names), support (support requests: who is support (`canHandle`), the handlers query, refs, emails to the support list and handlers, recipients, lists and badge counts), stations (pod stations: pairing state, the one pairing controller per location rule, the roster, placing a target pod from its first frame through a pairing controller), commandQueue (queued pod commands: one in flight per pod, resend on connect, acks, cancel; a target pod's commands through its controller), athletes (athletes, wristbands, assignments and loaners, bands presented to pods: check in and enrollment), firmware (pod firmware files in `storage/firmware/<image>/firmware.bin` with `firmware.json`: URL and MD5 for the `ota` command, the upload check and store for Administration > Firmware).
- `jobs/` minute and daily schedulers and their tasks (server stats, purge, offline periods, con/endpoint refresh, broker audit, never-connected unit cleanup); started only in the ingest process.
- `routes/` one router per area; `routes/account/` one file per account page, `list.js` is `/account` and the rest mount under `/account/<account uid>` along with the Analytics and Reports list pages (`unclaimed.js` also renders the location's Unclaimed view); `routes/api.js` bearer API mounted before sessions; `routes/provision.js` unauthenticated device first contact (`POST /provision/v1`), mounted above it; `routes/firmware.js` unauthenticated pod firmware downloads (`GET /firmware/<image>/firmware.bin`), mounted beside it; `routes/support.js` `POST /support` (the modal), `/support` (superadmins), `/support/<uid>` with its reply, status and files; `routes/account/support.js` Account > Support; `routes/auth.js` login with the sign in code step (`/login/mfa`, `/login/mfa/resend`), forgot password, reset and invite links; `routes/admin.js` also takes the per user MFA override (`POST /admin/users/<uid>/mfa`) from the MFA column on Account > Users.
- `middleware/` session (connect-session-knex, cookie `voltastc.sid`), csrf, auth chain (loadUser, requireBits), current account and location (from the URL or the loaded entity, never the session), errors (request id, `notFoundError()` for denied-or-missing), flash, eventLog (request and request_end rows, redaction, mounted twice in app.js).
- `nav/` menu tree (Monitor built per location) and breadcrumb builder, both unit tested.
- `realtime/` socket.io relay of the acct/ MQTT feed to the browser (`data` readings, `config` notices) and the superadmin only `/admin-logs` namespace for the live event log; runs in the web process with client id `<MQTT_CLIENT_ID>-web-<host>-<pid>`; `start()` attaches socket.io before listen, `connectFeed()` connects to the broker after settings load; `feedClient()` lends that connection to `mqtt/downlink.js`.
- `views/` EJS: `layouts/` shell, `partials/` shared pieces, one folder per area.
- `public/` theme css/js (`live.js` realtime hooks, `iot-table-tools.js` export/copy, `iot-bulk.js` bulk actions on list tables, `iot-sort.js` column sorting for `table.is-sortable`, `iot-title.js` the alarm title field: token insert and preview), images (`img/icon.png`, `img/site_logo.png`), vendor libs.
- `tests/` node:test unit tests for the pure parts (ladder, frames, nav, breadcrumb, metrics, permissions, passwords, tags, armed, levels, config values, device types, modules, topics and device ACLs, pod types and the JSON frame header, alarm titles, the rule change log and its read back, the API helpers, the API docs module, MFA sign in codes). Run `npm test`.
- `scripts/` operator scripts, run on the server from `/opt/voltastc` as the app user (they read `.env`; RDS and the broker's 1883 are reachable only from there): create-db, migrate, seed, `broker-bootstrap.js` (broker roles and users, `--settings` stores the MQTT site settings; passwords from the environment), add-gateway, `fake-station.js` (a fake controller or account pod and target pods for trying station pages, the command queue and wristbands before firmware: connect, pair, pods, ack, band, button, progress), `reset-test-unit.js` (removes a test unit completely; locally administered MACs only, dry run by default). `provision-test.sh` walks a unit through first contact and runs from any machine with mosquitto-clients.
- `deploy/` `install.sh` (Ubuntu 26.04 installer and re-deploy, safe to repeat), `nginx/voltastc.conf` (site template), `mosquitto/voltastc.conf` (broker conf.d snippet), `certbot-deploy-hook.sh` (copies the renewed certificate to Mosquitto, reloads both).
- `docker/`, `docker-compose.yml`, `Dockerfile`: local dev app and broker (dev database not settled yet).
- Root docs: `CLAUDE.md` (how to work here), `DECISIONS.md` (settled decisions), `STRUCTURE.md` (this file), `dynsec-broker-summary.md` (broker and provisioning, server side), `device-provisioning.md` (firmware guide to provisioning and reconnection), `pod-protocol.md` (the pod firmware contract: readings, config, queued commands, joining, ESP-NOW messages), `ALARM_TITLES_AND_RULE_LOG_README.md` (the port guide for alarm titles and the rule change log; DECISIONS says what was built and how it differs), `SITE_SETTINGS_SECTIONS_AND_SEARCH_README.md` (the port guide for the site settings sections, search and two row layout).
