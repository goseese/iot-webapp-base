# devmon decisions log

Settled decisions and their reasons. Read before changing anything listed; a later change should
add an entry here, not silently reverse one. Architecture reference: the iot-platform skill.

## Environment and deployment
- **Production is an IIS farm of two servers, IT-WebApp01 and IT-WebApp02**, behind the customer's ARR, which round-robins requests between them (Sep 2026, confirmed with `/health`). Each runs iisnode with `nodeProcessCountPerApplication="1"`, which limits processes per server only; overlapped app pool recycles also run two processes briefly on one server. So any number of app processes may be running at once, all with `ROLE` unset (`all`). `index.js` requires `app.js` for the iisnode entry.
- **One leader runs ingest and jobs, chosen by a SQL Server application lock** (`services/leader.js`, resource `devmon-leader`, exclusive, session owned, timeout 0, retried every 15 s). The lock lives on a dedicated tedious connection outside the knex pool, so SQL Server releases it when that connection closes and another instance takes over. The leader verifies the lock every 15 s with `APPLOCK_MODE` and exits the process if the check fails or the connection drops; iisnode restarts it on the next request. Every process serves web pages and runs its own realtime relay. Without this, each instance ran the MQTT ingest and minute jobs (duplicate alarms and emails) and the ingest clients kicked each other off the broker every 5 s.
- **Migrations and seeds run under a second application lock** (`db/applock.js`, resource `devmon-migrate`, exclusive, session owned, waits up to 10 minutes). Every farm member boots at once; one migrates and seeds while the others wait behind the 503 "starting" page, then find nothing pending. The helper sets tedious `requestTimeout` above the wait, because tedious cancels any request after 15 s by default. A web-only process still never migrates or seeds. Not covered: `ensureDatabase` runs before the lock (an app lock lives inside the database), so two servers first-booting against a missing database can race there; only a brand-new install is affected.
- **Open item for the customer's admin:** app pool idle timeout 0 and start mode AlwaysRunning on both servers. The IIS default idle timeout (20 minutes) can leave no process, and so no leader, when there is no traffic.
- **`PORT` is a named pipe under iisnode** and is passed to `listen()` untouched; never `Number(PORT)`, never bind a host.
- **IIS passes Node's error responses through** (`<httpErrors existingResponse="PassThrough" />` in `deploy/web.config`, Sep 2026). Without it IIS replaced every non 200 page with its own bare text: a 422 form error showed "The custom error module does not recognize this error" and a 410 dead link showed "The page you requested was removed". Found on the password reset flow; login failures, 404 and 500 pages were affected the same way. **Reversed Sep 2026:** the customer's server admin has directed that PassThrough will not be allowed on the WebApp servers once the site goes live, so the element was removed from `deploy/web.config` and must not be added back. See "Every reply leaves the app with status 200" below. This entry stays because it records exactly what IIS does without PassThrough.
- **Every reply leaves the app with status 200** (`middleware/httpStatus.js`, Sep 2026), because the entry above was reversed and IIS is back on its default `existingResponse="Auto"`. IIS preserves the status line and replaces only the body, so what was actually lost was the login error, the 422 form re-renders that carry validation messages, the 410 dead link pages and the JSON `{ error }` bodies; machine callers reading the code alone were unaffected. The middleware wraps `res.status()` and `res.json()` once, mounted immediately after `requestId` in `app.js`, so it also covers codes we do not raise ourselves (body-parser 400 and 413, CSRF 403, Express's own 404). The real code goes out in the `x-app-status` header, and for JSON as `status` next to `ok:false` in the body. Nothing in the app calls `res.sendStatus()` or assigns `res.statusCode` (checked Sep 2026), so `res.status()` is the only path a code can take. Redirects are untouched: 3xx never reaches the branch and IIS does not intercept them anyway. `/health` is the single exemption, because `deploy/deploy.ps1` aborts a deploy on a non-2xx and the cluster probe uses the code to pull a failed server out of rotation, while nothing reads its body. Client side, branch on `x-app-status` or on the body, never on `res.ok`; `views/partials/notification-modal.ejs` checks both so it stays correct either way. Setting `ENABLED` to false in the middleware reverts the whole thing in one edit if PassThrough is ever allowed again.
- **HTTP listens before boot.** Migrations, seeds and settings load after `listen`; until done every request gets 503 "starting" and `/health` reports `starting` / `boot failed` with the reason. iisnode otherwise times out and hides the real error. Unhandled rejections are logged, not fatal.
- **TLS is terminated before Node** (ARR, then iisnode). `trust proxy` is `true` in production and `X-ARR-SSL` / `x-iisnode-https` are mapped to `X-Forwarded-Proto`; without this the Secure session cookie is never set and login loops.
- **`.env` is committed and holds production values** (customer convention: deploy by push, secrets in repo). Dev uses `.env.local` via compose `env_file` + `DOTENV_CONFIG_PATH`; `config/env.js` passes that path to `dotenv.config()` (which ignores the variable on its own), so a key missing from `.env.local` is missing in dev, never taken from the production `.env` (found Sep 2026 when commented MQTT lines fell through to production's client id). Any `.env` change locally needs `docker compose up -d --force-recreate app` (restart does not reread it).
- **Production database is `dtmprod`**, dev uses a different one; sharing a database between two instances double-notifies every alarm. Boot creates the database if the login can (`db/createDb.js`). The leader lock is per database, so dev and production never compete for it.
- `SEED_SUPERADMIN_PASSWORD` seeds the first superadmin on a fresh database (no access to iisnode logs); the account is confined to the set password page until changed.
- Static assets carry `?v=<commit or boot time>`; production caches them 7 days. Commit comes from `public/build-info.json` (customer pipeline, Sep 2026: also gives build number, branch and build time), then `build.json`, `GIT_COMMIT`, or `.git`; with none of them the `?v=` falls back to boot time. The footer shows version and uptime; build number, commit, branch, build time and start time are in its hover text. `build-info.json` is publicly readable because it sits in `public`, in line with `/health` below.
- `/health` is unauthenticated on purpose (pipeline health check, quick "did my push land"); it returns version, commit, boot time, host name, process id and whether that process is the leader. A curl loop against it shows which farm member answered and which one holds the lock. Strip those fields if that ever matters (host names are internal server names).

## MQTT and broker
- **MQTT topics live in `mqtt/topics.js`** and nowhere else. Device namespace is `dev/{device_guid}/frame|ble|status` up (extended Sep 2026 with `data`, `config/{key}` and `geoscan`, see "Gateway uplinks split by purpose" below), `dev/{device_guid}/cmd` down (broker ACLs scope the subtree `dev/{guid}/cmd/#`, which also matches the bare topic, so sub topics need no ACL change), for any credentialed device (gateway, wifi direct, cellular direct), not just gateways. `acct/{account_guid}/#` is server published, `provision/request|response/{hw_id}` unchanged. `dom/#` and `dtm/#` are reserved for the legacy adapter only and the parser rejects them, so new traffic never mixes with the legacy namespace. Note: the broker has no `acl_file` today (checked Sep 2026), so the shared `device` credential is not actually confined to any prefix; do not rely on broker ACLs until one is added.
- **Broker `iot.datatelematics.io`** (Ubuntu host `it-ubuntu-iot`, mosquitto 2.0.18): we may change the mosquitto config and password file, but not add or change ports (1883 plain, 8883 TLS). Dynsec is installed on the broker and driven by `services/broker/dynsec.js` (Sep 2026). The active driver is the `BROKER_DRIVER` site setting, default `static`, under which provisioning hands out the GUID only and gateways keep the shared `device` credential (`services/broker/static.js`). See the dynsec entries below.
- **The platform connects as broker user `devmon_server`** (created Sep 2026). `server_admin` belongs to the broker host's own Node daemon and must not be reused, or the two clients collide.
- **MQTT client ids:** the ingest client uses `MQTT_CLIENT_ID` (`server-devmon.datatelematics.io`) with a persistent session; only the leader connects with it, so the session carries over on failover. The realtime relay uses `<MQTT_CLIENT_ID>-web-<host>-<pid>` with a clean session, unique per process, because every instance needs its own feed. Two connections with the same client id kick each other off the broker regardless of username.
- **Broker TLS certificate on 8883** comes from the certbot lineage `iot.datatelematics.io-0001` (RSA). A deploy hook, `/etc/letsencrypt/renewal-hooks/deploy/mosquitto-certs.sh`, copies `fullchain.pem`, `chain.pem` and `privkey.pem` into `/etc/mosquitto/ca_certificates/` (the paths `mosquitto.conf` uses), owned by `mosquitto`, then reloads the broker. The old copies were made once and never refreshed, expired April 2024, and blocked the platform until Sep 2026. Do not delete the `-0001` lineage as a duplicate of `iot.datatelematics.io`; the hook depends on it. The chain now comes from Let's Encrypt's Generation Y hierarchy (YR2, Root YR cross-signed by ISRG Root X1).
- **Legacy fleet:** devices pinned to the pre-2024 certificate were the reason the old cert was kept. After a broker restart (Sep 2026) only gw7080 gateways (updatable root CA), a development gateway, and the broker host's own daemon reconnected, so no pinned devices remain in use.
- **MQTT connection settings live in site settings** (Admin > Site settings > MQTT, Sep 2026): `MQTT_HOST`, `MQTT_PORT`, `MQTT_TLS`, `MQTT_USER`, `MQTT_PASSWORD` (secret, encrypted) and `MQTT_CLIENT_ID`, read only through `mqtt/broker.js`. An `.env` key of the same name still wins and shows read only; the MQTT lines stay commented out in `.env` and `.env.local` so each database holds its own values (dev and production must never share a client id). A blank `MQTT_CLIENT_ID` falls back to `server-<APP_URL host>`, identical on every farm member, so the ingest session carries over on failover (the old fallback, the OS host name, differed per server). Changes apply without a restart: every process polls the newest `updated_epoch` of the mqtt rows every 15 s (`mqtt/watch.js`) and reconnects its ingest client (leader only) and realtime relay. iisnode `watchedFiles` and `recycleSignalEnabled` were rejected: they recycle one farm server only and need changes to the customer's `web.config`. Changing the client id leaves the old persistent session on the broker until it expires. The realtime relay connects after boot loads settings (`realtime.connectFeed()`), not at listen time. A blank `MQTT_HOST` leaves ingest and relay unconnected with a warning.
- **Device provisioning is an unauthenticated router at `/provision/v1`, not part of the API** (Sep 2026). `routes/api.js` puts `apiAuth.authenticate` on its whole router, so a device on first contact, holding no key, would be refused before reaching a handler. `routes/provision.js` is mounted above `/api/v1` in `app.js`, which also puts it ahead of session and CSRF, and `routes/api.js` keeps its bearer only contract unchanged. The router answers JSON for every path under its mount and carries its own error handler, because `middleware/errors.js` renders an HTML page for anything outside `/api/` and a device must never be sent one. Rate limited per IP by `PROVISION_RATE_PER_MINUTE` (default 10) with an in process bucket dropped whole each minute; the map is keyed by caller IP, which is unbounded, so it is reset rather than aged per entry as `services/apiAuth.js` does with credential ids. The ceiling is per farm process and `trust proxy` is on, so treat it as a flood brake, not a security control. Issuing is `services/provisioning.issue()`; see "Credentials are issued synchronously" below.
- **First contact runs over a retained `con/endpoint` message** (Sep 2026, `services/connectEndpoint.js`). The web app and the broker are on different hosts, so firmware carries the broker host only and learns the provisioning URL from a retained message it reads as the shared `announce` broker user, whose role can read that one literal topic and nothing else. Payload is `{ url, published }`; the date exists so a human with `mosquitto_sub` can see whether the message is current, and firmware ignores it. The path is the `PROVISION_PATH` site setting, the host is not configurable and comes from `APP_URL` through `mqtt/broker.provisionUrl()`, so the message always names this server. Published by the leader only, on every ingest connect and once a day from `jobs/tasks/connectEndpoint.js`. `mqtt/watch.js` deliberately has no call of its own: a settings change already ends in `client.reconnect()`, and publishing there as well would fire at a connection being torn down. Both provisioning settings sit in the `mqtt` settings group because that is the group `mqtt/watch.js` polls, which is what makes a path change reach the broker within 15 seconds.

- **The dynsec driver may run in any farm process** (Sep 2026, `services/broker/dynsec.js`). This reverses the line in `dynsec-broker-summary.md` that followers never connect as admin. Each process connects as the dynsec admin user with its own client id, `<MQTT_CLIENT_ID>-dynsec-<host>-<pid>`, and a clean session, the realtime relay's pattern: `MQTT_CLIENT_ID` is identical on every farm member by design, so a shared id would let two processes evict each other off the broker, and the clean session means a pid that changes on every restart leaves no orphan session. Several admin connections at once are safe because replies are matched by `correlationData`. Facts verified in the mosquitto 2.0.18 plugin source, the deployed version: success is the absence of an `error` key (`plugin.c:230`); replies are published to every subscriber of the response topic with a NULL client at QoS 0 (`plugin.c:252`), so correlation is mandatory, `mosquitto_ctrl` replies arrive too and are ignored, and replies can be lost, hence a 10 s timeout on every command and idempotent operations; a failing command does not abort its batch (`plugin.c:735`). Tolerated errors are exactly `Role already exists` (then `modifyRole`, which replaces the ACL set and so repairs a stale role), `Client already exists` (then `setClientPassword`), `Client not found` and `Role not found` on delete. Every create reads the role back with `getRole` and throws if an ACL is missing. Settings in the `mqtt` group: `BROKER_DRIVER` (moved out of env so it can be switched without a deploy), `MQTT_DYNSEC_USER`, `MQTT_DYNSEC_PASSWORD` (secret); `mqtt/watch.js` reconnects the driver on a change.
- **Credentials are issued synchronously** (Sep 2026, `services/provisioning.issue()`). The broker account is created before the row is activated, on whichever server took the request, so a device is never handed a password for an account that does not exist. Order: claim the row with one conditional update from `pending` to a transient `issuing` (activated_epoch holds the claim time; a claim older than 60 s counts as abandoned), create the account, then activate. The claim exists because the broker round trips make the request slow enough for a firmware retry to overlap its first attempt, possibly on the other server; without it both would set different passwords and the device could keep the one the broker discarded. A broker failure returns the row to `pending` and reaches the device as a 500, and it retries the HTTPS call; a lost reply is safe because the retry hits "already exists". Firmware should allow about 20 s for the request. Rejected: the asynchronous follower approach (leader only dynsec, a `broker_created_epoch` work list and a minute job), which was only needed while followers could not connect; it was built and discarded before commit. Superseded in part by the unit model below: the claim now covers first contact too (the INSERT of the new credential row is the claim, the unique MAC index lets one request win), and there is no longer a refusal for unknown hardware.
- **Device ACLs keep subscribe and receive together** (Sep 2026, `mqtt/topics.deviceAcls()`). The broker defaults `publishClientReceive` to deny, so a role with a subscribe ACL and no receive ACL lets a device subscribe, be granted its QoS, and then silently never receive a command. Both are emitted by one loop over `DOWNLINK_TOPICS`; add a downlink topic there, never push a single ACL by hand. Role ACL types must be the specific ones (`subscribePattern`, `subscribeLiteral` and so on); plain `subscribe` and `unsubscribe` are only valid for `setDefaultACLAccess`.
- **Gateway uplinks split by purpose** (Sep 2026, `mqtt/topics.js`, `pipeline/identify.js`, `deviceTypes/gw7080.js`). Extends the namespace entry above with three uplinks, settled with the gw7080 firmware: `dev/{guid}/status` is connectivity: the connect message (connect event, csq, ipa, `firmware`) retained, nwinfo and radio mode not retained, LWT `{"online":false}`; `dev/{guid}/data` carries the device's own readings and the reboot reason, not retained, mapped by the type's `dataMap` using the firmware's existing `publishStatus()` keys unchanged (the device never sends `batt_pct`; battery and signal percent are computed on the server, see "Battery and signal percent"); `dev/{guid}/config/{key}` carries one config value per publish with the key in the topic, not retained, sent on every connect; `dev/{guid}/geoscan` carries the wifi and cell scan, not retained. `frame` and `ble` are unchanged. This deviates from gateway-protocol 4.4, which puts the gateway's own readings in the retained status: readings are a time series and a retained topic holds current state, and keeping status to connectivity leaves the LWT on a topic that means only "connected or not". 4.4 still works for any type that declares a `statusMap` (`gateway_generic`). Config is deliberately not retained, so a broker restart does not replay every gateway's configuration; the gateway sends it on connect. The firmware key stays `firmware` (what the legacy servers read); ingest accepts `firmware` or `fw`. The keyed kind is `KEYED_UPLINK_KINDS` in `topics.js`, whose ACL is the pattern `dev/{guid}/config/+` (dynsec matches ACL topics as filters) and whose parse returns `key`; `config/` with an empty key or extra levels is rejected. Config and geoscan are accepted and logged at debug only; storage and the location lookup are not built. Existing units keep their old role until Reprovision, and the daily broker audit flags them until then.
- **Retained replays never count as contact** (Sep 2026, `mqtt/client.js`, `pipeline/identify.js`). The ingest client subscribes on every connect, and per MQTT 3.1.1 3.8.4 a SUBSCRIBE that replaces an existing subscription makes the broker re-send every matching retained message, so every reconnect (broker restart, failover, settings change, network blip) redelivers every unit's retained status. Those copies arrive with `retain = 1` (3.3.1.3), live publishes to an existing subscriber with 0. Ingest passes the flag through: a retained status only refreshes firmware, never last seen, readings or the registry. The subscribe call itself was left as is.
- **Sensors are created on first value, not when a device is added** (Sep 2026, `pipeline/index.js`, `services/devices.createSensor`). Deviates from architecture 3.2, where device creation seeds every channel. A value for a channel the type declares, on a device with no sensor row for that channel, creates the sensor in its own transaction and is stored in the same pass. Only live rows count: a deleted sensor comes back as a new sensor (new uid, no history) with the channel's next value (reversed Sep 2026, it used to count deleted rows too; see "Sensor delete and hide"). Only a usable value creates one (a finite number or a boolean; nulls such as `int_temp` on a board without an SHTC3 do not). A device therefore only has the sensors it actually reports, and a channel added to a type module later appears with its first value on existing devices. `sort_order` is the channel's position in the type's list. Two writers racing on one channel are settled by `ux_DTM_sensors_channel`; the loser logs a warning and re-reads.
- **Default alarms are declared per channel, and there is no default no-data rule** (Sep 2026, `services/devices.createSensor`, validated in `deviceTypes/index.js`). A channel's `defaultAlarms` holds threshold entries as before and `{ rule: "no_data", timeoutSecs, severity? }` entries; a channel with none gets no alarm rules at all. The type level `noDataTimeoutSecs` (which put a no-data rule on every sensor, so once per boot values like `reboot_count` would sit in permanent no-data) and the channel level `noDataTimeoutSecs` are gone, and `validate()` refuses a module that still carries either. `platform_server` and `gateway_generic` keep their old behavior by appending the no-data entry to every channel in their own module; `gw7080` puts it on `vin` only (3600 s; the PHP model's `no_data_timeout` was 60, taken as minutes).
- **`cmd_ack` is an uplink** (Sep 2026, `mqtt/topics.js`). Firmware publishes `dev/{guid}/cmd_ack` when it hears a command (ble enable/disable, charge, join, queued node commands); before this the broker dropped every one. Logged by ingest for now, for the Commands tab later. A geoscan command has no ack: the geoscan publish is the reply. Existing units need Reprovision for the ACL; the daily audit flags them until then.
- **Gateway config is kept per unit, written without retained messages** (Sep 2026, migration 0021, `services/unitConfig.js`, `/devices/:uid/config`). One `DTM_unit_config` row per MAC and key: `reported_*` from `dev/{guid}/config/{key}`, and `desired_*` for a write from the page that the unit has not confirmed. A write publishes `dev/{guid}/cmd/set_config/{key}` with the bare value (the firmware's existing command, covered by the `cmd/#` ACL), QoS 1, not retained; the firmware saves it and publishes `config/{key}` with the value it now holds, and a match clears the pending state. Retained was rejected: clearing a retained message is a zero byte publish that every subscriber, the gateway included, receives as a message. A unit that was offline gets every pending write again when ingest sees its live connect message, and the page can cancel a pending write. The echo is the stored form, not what was sent (hex list without spaces and lower case, `%.1f` floats, `true`/`false` for any accepted boolean), so both sides are compared after `services/configValues.normalize()`, and the page sends the normalized form. Which keys exist, their kind, and whether they are writable, advanced or need a confirm live only in the type module's `configKeys`; flipping `writable` is the whole change to open a key. `ble_relay_mode` reboots the gateway without replying, and is confirmed by the full config publish after it reconnects. Publishing goes through `mqtt/downlink.js`, which uses the ingest client on the leader and otherwise the realtime relay connection every web process has (`devmon_server`, role `legacy_full`, may publish anywhere), so a Save works on any farm server. String lengths and numeric ranges come from the `EEPROM_CONFIGS` struct in the firmware's `config.h` (`maxLength`, `min`, `max` on each key), because the gateway silently truncates a longer string or wraps an out of range byte, and the echo would then never match; 99 characters (the firmware's confirm buffer) is the ceiling for any key.
- **Incoming messages never change a device's offline state** (Sep 2026, `pipeline/identify.js`). `is_offline` is set with intent by a person (device Settings) or a scheduled offline period, and only those, with `jobs/tasks/offlinePeriods.js`, change it. Ingest used to write `is_offline: 0` on every live status message; the minute job then set it back because the period was still open, so a gateway reconnecting during maintenance had its alarms armed for up to a minute at a time and cleared again. A device that goes up and down while being worked on now stays offline for the whole period.
- **The config page updates live from a notice, never from values** (Sep 2026, `services/unitConfig.notify`, `realtime/index.js`, `views/devices/config.ejs`). Every change to a unit's config rows (a reported value, a save, a cancel, a confirmed write) publishes `acct/{account}/config` with `{ event: "config", device }` through `mqtt/downlink.js`, so it works from ingest on the leader and from a save on either farm server. Each web process's relay subscribes to `acct/+/config` and emits `config` to the account's socket.io room; the page, on a notice for its own device, fetches `GET /devices/:uid/config/rows` (same `loadDevice` checks as the page) and swaps the rows in. Values never go over the socket or MQTT, because the account room and the `acct/` namespace reach every member of the account, including users without access to that location, and config holds WiFi passwords. The fetch is debounced one second (a gateway publishes every key about half a second apart on connect), a row the user has focused or edited without saving is left alone, and a response with no rows (an expired session answering with the login page) is ignored. The row markup lives only in `views/devices/config-rows.ejs`, which both the page and the rows route render. `live.js` exposes its socket as `window.iotSocket` for page scripts.
- **BLE uplink is one beacon per publish** (Sep 2026, `pipeline/identify.handleBle`). Deviates from gateway-protocol 4.3, which sends one batch array per period: some sites have 200+ beacons, and a batch that size could not be sent by the gw7080 (PubSubClient buffer, 512 bytes). The topic stays `dev/{guid}/ble` (already in every unit's ACL; moving it to `data/ble` would force a Reprovision of every unit and `data` already means the unit's own readings). Payload keeps the firmware's existing keys, only the topic moves from the legacy `/dom/{mac}/frame/node/ble`: `{ dmac, rssi, count, data }`, `data` the advertisement bytes in hex as captured by the firmware (the sample starts `AAFE`, the Eddystone service UUID), `count` ignored for now. With no age in the message the observed epoch is the receipt time; firmware may add `seconds_ago` and the server uses it. A 4.3 batch is still accepted for types that follow the skill. Beacons are parsed by the `kind: "beacon"` type modules' `parseAdvertisement()`; the first is `ble_s5` (Eddystone 0x21, versions 04 and 00, ported from the legacy PHP `ble_s5` model and checked against two legacy samples in `tests/ble_s5.test.js`), which added the `acceleration` metric (g, inbound mg). Its channel ids follow the channel naming standard below (`int-vbat`, `int-temp`, `acc-x`). RSSI and the heard `count` are stored per hearing gateway (see "Per gateway sensors" below). Not ported: the legacy server computed `ewma-temp` and `heat-index`. The legacy `22:00` type (`ews_pir_tcm`) is not ported yet.
- **Per gateway sensors** (Sep 2026, `deviceTypes/index.js` `gatewayChannelId`, `gatewayValues`, `channelDef`). What a gateway measures about a device it hears (RSSI, BLE heard count) is one sensor per hearing gateway, the legacy naming: a channel declared `perGateway: true` is stored as `{id}-{last two bytes of the gateway MAC as xx:xx, lower case}` and named `{name} {XX:XX}`, the legacy `%02X:%02X` (gateway A846749F72B4 gives `rssi-72:b4`, "RSSI 72:B4"; also `signal-72:b4`, `heard-count-72:b4`). Colons are safe: channel ids appear only in pages and JSON, never in URLs or MQTT topics. One mixed `rssi` sensor was rejected: readings from several gateways on one chart are meaningless. The per gateway channel resolves to its declared channel through `channelDef()` (metric, units, default alarms, sort order), which the pipeline, `createSensor` and the sensor page use; a suffix on a channel not declared `perGateway` is rejected. The sensor follows the gateway's hardware, so a replaced gateway starts new sensors and the old ones stop. Written for every hearing gateway before dedup, as the LoRa RSSI already was (architecture 3.6); `handleFrame` uses the same helper, so a node type that declares `rssi` `perGateway` gets the same.
- **Channel naming standard** (Sep 2026, enforced in `deviceTypes/index.js`). A channel id says what the reading is in terms that fit every device, lower case words joined by hyphens, so the same kind of reading has the same id on every type: `int-vbat` the device's own battery (V), `int-vbat-pct` its percent, `vin` external power in ("External Vin"), `int-temp` / `int-humidity` board mounted, `ext-temp-1..n` external temperature probes (an RTD is `ext-temp-N` too, the type's channel `description` says what kind), `ext-sw-1..n` external switches, `pir-motion`, `acc-x|y|z`, `cycles`, `run-time`, the device's own radio raw as `csq` or `wifi-rssi` and as a percent `signal`, and what a hearing gateway measures per gateway (`rssi-xx:xx`, `signal-xx:xx`, `heard-count-xx:xx`, see "Per gateway sensors"). Pick the global name before adding a new kind of sensor, and add it to this list. The firmware's own payload keys never change: `dataMap` or the parser maps them to the standard ids (gw7080 `vbat` -> `int-vbat`, `modem_csq` -> `csq`). `platform_server` and `gateway_generic` predate this and set `legacyChannelIds: true`, because they have live sensors; gw7080 and ble_s5 were renamed without a migration (their sensors were test data, deleted by hand).
- **Battery and signal percent** (Sep 2026, `services/levels.js` tables, `pipeline/levels.addLevels`, migration 0022). Ported from the legacy PHP helpers, tables and interpolation unchanged (1..100, clamped at the end points). `int-vbat-pct` comes from `int-vbat` and the battery chemistry: the device's `battery_chemistry` (Settings tab, Battery), else the type's `batteryChemistry` (ble_s5 `cr2477`, gw7080 `li_ion`); temperature correction uses `int-temp` from the same message or its last value (`temp_coef` is 0 in every table, so it is off until measured). A channel declaring `signal: "lora"|"ble"|"csq"|"wifi"` gives `signal` with the same per gateway suffix (`rssi-72:b4` -> `signal-72:b4`; the gw7080's own `csq` or `wifi-rssi` -> `signal`). Computed in the pipeline before sensors are created and stored as ordinary readings in the same message (as the legacy server did), only for channels the type declares, never over a value the message carries. Two tables are not from the legacy code: `li_ion` is PROVISIONAL, a generic 3.7 V cell curve (4.2 V 100%, 3.9 V 75%, 3.7 V 50%, 3.5 V 25%, 3.0 V 0%) until we have the gw7080 cell's datasheet, and a gateway on external power reads its charging voltage, so it shows high; `wifi` is Microsoft's WLAN signal quality mapping (-50 dBm 100, -100 dBm 0, linear).
- **Device commands are declared by the type and gated per command** (Sep 2026, `deviceTypes/*.commands`, `routes/devices.js`, `views/devices/commands.ejs`). A Commands tab lists the type's `commands`, each published to `dev/{guid}/cmd/{name}` (`topics.device.command`) with the firmware's own name, so the existing `cmd/#` ACL covers it and no Reprovision is needed. The button shows a user facing `label` (gw7080 `publish_now` is "Get data"). Each command names its own permission bit: Get data needs only `view`, because it just makes the gateway report; disruptive commands (reboot, join, firmware) will name `edit` and set `confirm`. A user sees only the commands they hold the bit for, the tab is hidden when that is none, and the POST checks the bit again (denied looks like missing). Commands are sent now through `mqtt/downlink.js` and never queued or retained, unlike config writes: a reboot or firmware update arriving hours later on reconnect would be a surprise. `cooldownSecs` (60 for Get data) limits sends per device across users and farm servers, read from `device_command` rows in the activity log, because any viewer can now make a cellular gateway publish. Reprovision stays on Settings: it acts on the server and broker, not on the unit.
- **A daily audit checks the broker against the database** (Sep 2026, `jobs/tasks/brokerAudit.js`). One `listRoles` with `verbose: true` returns every role with its ACLs in a single round trip, then each UNIT holding its own account, placed or not, is checked for its `dev-{guid}` role (the GUID is `broker_username`, never a device row uid) and every ACL `deviceAcls()` produces. The result goes in `broker_fault` and `broker_checked_epoch` (migration 0019) and shows as a banner on the device page of the unit's current placement, naming the consequence and pointing at Reprovision; the fault lives on the unit, so it follows the hardware. Detect only, by choice: the fix is Reprovision, which rebuilds the account through the same verified path as a first provision. `issue()` and `reset()` clear the fault, since each replaces the account it described. Skips rows with no password (static era devices on the shared credential). Checks roles, not clients; a missing client is loud anyway because the device cannot log in.

- **Broker identity belongs to the unit, not the placement** (Sep 2026, migration 0020, `db/repos/credentials.js`). Reverses the identity model's "the MQTT username is the device table GUID, `device_credentials` is a 1:1 extension of the device row", architecture 7.3 ("admin adds the MAC first; unknown hardware gets nothing"), and the spec's open item that archive must remove the broker account. A **unit** is one physical piece of hardware keyed by MAC: its `device_credentials` row holds the broker username (a GUID, the one in `dev/{guid}/...`), the password and the state, and lives across placements. A **placement** is a `DTM_devices` row, one stint at one location, owning sensors, history and alarms; its uid is no longer a broker identity. A unit's current placement is not stored: it is the one live, unarchived device row holding its MAC, which `ux_DTM_devices_hardware_id` already allows exactly one of. Consequences, all deliberate:
  - **Every unit gets credentials on first contact**, placed or not, so firmware can be flashed, provisioned and shipped. `POST /provision/v1` takes `{ hw, model, fw }`. `model` is required and decides the device type: the `deviceTypes` module whose `models` list contains it (exact match, `deviceTypes.forModel()`), which must be of kind gateway or direct and never `platform_server`, else 400. A separate `type` field was built first and dropped the same day: it duplicated the model and let firmware send a pair that disagreed. A new product needs its model string added to a type module before its units can provision. Three answers: no credential, a new unit (guid + password); pending (after Reprovision or lost flash), a fresh password under the same GUID; active, `{ existing: true, guid }` and the device keeps what it has. The endpoint therefore confirms that a MAC is a unit and returns its GUID to any caller. Accepted: the GUID is the broker username and appears in every topic, so it is not a secret, and seeing what GUID a unit believes it has is useful for troubleshooting. The password is never re-sent. 409 means another request is issuing that unit; retry in a few seconds.
  - **Adding a device creates no credential**; claiming is just adding the MAC somewhere, and a unit that already holds credentials starts delivering at once with nothing done on the device.
  - **Archive, delete and location delete leave the unit alone.** Its credentials keep working and it stays connected; its data is dropped because there is no placement. Ingest (`pipeline/identify.js`) resolves topic GUID to unit to current placement and logs unclaimed traffic at debug; an unclaimed unit's status still updates `device_registry.last_firmware`. A topic GUID that no unit holds falls back to the old device uid lookup, for hardware provisioned before this change.
  - **Revoking is Reprovision** (`provisioning.resetUnit(mac)`): deletes the broker account and flips the unit to pending. On the device settings page for placed units, and on Admin > Unknown devices for unclaimed ones.
  - **`device_id` on credentials is dead**: nullable, its unique index dropped (SQL Server's plain unique index admits a single NULL), never written, never joined. Look a unit up by MAC or by `broker_username` (unique among live rows).
  - **The legacy MQTT `provision/request` path runs through `issue()`**, taking the type from the unit's placement, then `deviceTypes.forModel()`, then `gateway_generic`, passed to `issue()` as an override so fielded firmware is never refused for an unlisted model string (the only path allowed to bypass the model rule); it still answers only when something was issued. Delete it once the gw7080 firmware update ships.
  - **Unclaimed units that never connect are cleaned up** (`jobs/tasks/unitCleanup.js`, daily): issued more than 30 days ago and `mqtt_seen_epoch` still NULL (stamped by ingest on a unit's first message), so the broker account is deleted and the credential soft deleted. The registry row stays, per architecture 3.8. Existing active rows were stamped as seen by migration 0020 so live gateways are never caught. The endpoint being unauthenticated means anyone can mint units for made up MACs; each is contained to its own topic tree by its ACLs, and the cleanup bounds how many accumulate.
  - **Firmware guide:** `device-provisioning.md` is the device side of all of this, written to be handed to firmware work. It supersedes `gateway-protocol.md` section 2 (MQTT bootstrap provisioning, pending rows, unknown MACs get nothing) and the client id line in section 1; the skill reference itself was left unedited. Settled Sep 2026: MQTT client id is `{model}-{mac}` (e.g. `gw7080-7c4fad842518`); the provisioning site uses a Let's Encrypt certificate, so firmware pins ISRG Root X1 for both HTTPS and the broker. Open items for firmware (HTTPS root CA, client id, clean session, gw7080 type) are listed at the end of that guide.
  - **Firmware contract**, codes in `x-app-status` over HTTP 200: 200 with password, store it; 200 with `existing`, keep yours; 400, bad request, do not retry; 409, retry in seconds; 429, retry after the minute; 500, retry with backoff. Allow about 20 s per request. On `existing` with MQTT logins that keep failing, back off: that is lost flash or a broken account, and the fix is Reprovision.

## Data and schema
- Tables are `DTM_` prefixed through `T()` in `db/knex.js`, the only place the prefix lives. Columns that collide with T-SQL keywords use suffixes (`query_json`, `output_kind`, `definition_json`, `setting_key`).
- `insertId()` normalises `.returning()` results; `notFoundError()` is the only way to deny (denied and missing look identical).
- Settings: `.env` key of the same name overrides the database and shows read only in the UI. Secrets are AES-256-GCM with `SETTINGS_KEY`; never rotate it once anything is encrypted.
- Mail and SMS providers are drivers that declare their own settings (`settings: [...]`), grouped into the Email and SMS tabs. The `none` driver records `suppressed`, never `sent`. Every send writes `DTM_notifications` first, then the outcome, the message body and the provider's raw answer.
- **`DTM_devices.hardware_id`** (was `mac`), `NVARCHAR(255) NULL`: the string that identifies the hardware (MAC for radio kinds, host name or IMEI for direct devices), never an FK and never the display name. Filtered unique among live, unarchived rows (`ux_DTM_devices_hardware_id`), global not per location; archived and deleted rows keep theirs. `device_credentials.mac` and `device_registry.mac` are unchanged (credentials only exist for MAC-identified hardware). The `platform_server` device's id is `new URL(APP_URL).hostname`; seed 0004 and the server stats job look it up by hardware id, never by name (renaming the device once created a duplicate).
- **Sensor description** (Sep 2026): `DTM_sensors.description NVARCHAR(MAX) NULL`, where NULL inherits the device type channel's optional `description`. Plain text, line breaks kept, edited in place on the sensor Overview (edit permission). Saving the default text unchanged, or saving empty, stores NULL, so later changes to a type's description still reach sensors that never customised it. Written for specialised sensors such as the platform server's, not expected on every sensor.
- Location `alarm_mode` is `active | muted | offline`. Muted evaluates and records but notifies nobody; offline evaluates nothing (no thresholds, no no-data, no escalation timers) and clears active alarms when set. `notifications_muted` is kept in sync as the notification gate.

## Navigation and UI
- **Location first.** `/locations/<uid>` is the location dashboard; the sidebar Monitor section exists only while inside a location and every link carries the uid (shareable support links). Cross-location list pages were removed; old paths redirect. Analytics and Reports are account wide, under Manage (their list pages are under `/account/<uid>/`, see the next entry).
- **Every page rebuilds from its URL; the session holds no navigation state** (Sep 2026, `middleware/account.js`, `routes/account/index.js`, `nav/menu.js`). Extends "Location first" to accounts. A user can paste any link to support and it opens exactly what they saw. `session.accountId` and `session.locationId` are gone: before this, `/account` and every account page showed whichever account was last touched, because opening a location, the account switcher and Admin > Accounts > Open all rewrote the session. Rules:
  - `/account` always lists the accounts the user can view, even when there is one (a superadmin adds accounts there too). Login and `/` land on it. Each account's pages live under `/account/<account uid>/` (overview, locations, users, alert groups, API, unclaimed, settings, analytics, reports); `loadAccount` checks the uid against the user's visible accounts, and anything else is `notFoundError()`. Old paths (`/account/locations`, `/dashboard`, `/devices` and the like) redirect to `/account`, since they carry no account.
  - A detail page needs only its own uid: `/locations/<uid>`, `/devices/<uid>`, `/sensors/<uid>`, `/alarms/<uid>`, `/analytics/charts/<uid>`, `/analytics/dashboards/<uid>`, `/reports/<uid>`. The account and location come from the row (`enterLocation`, `useAccount`), and a row whose account the user cannot view is not found. This also closed a gap: chart and dashboard loaders never checked the account.
  - The sidebar's Account link is always the list; its children and Analytics and Reports carry the page's account uid and appear only while a page belongs to an account. The account switcher dropdown and the Admin > Accounts Open button were removed; the account name links to `/account/<uid>`.
  - The sidebar alarm badge sends `?location=<uid>` to `/alarms/count.json`, which used to read the session's location.
- Breadcrumbs are `Account / Location / ...`, built by `nav/breadcrumb.js` (tested), resolved at render time from `req.originalUrl` (router-relative `req.path` broke this once).
- Inline page scripts must run on `DOMContentLoaded`: vendor libraries load at the end of the body. This bit three times (echarts, datatables, bootstrap modal).
- Theme variables everywhere; Bootstrap `bg-body-tertiary`, `text-bg-light` and simple-datatables' own chrome are overridden in `iot-theme.css` because they paint light on the dark theme.
- Relative time labels carry `data-epoch`, tick every 30 s in `live.js`, show a browser-local timestamp on hover with the help cursor and dotted underline. The same look is the `.iot-hint` class for any element with details in its `title` (footer version).
- **Charts always show alarm thresholds by default** (Sep 2026, `views/sensors/show.ejs`). Users assume a limit does not exist if they cannot see it on the graph. The y axis spans the visible data plus every enabled threshold, with a 5% margin past the outermost one, and bounds rounded to ECharts' own tick steps (1, 2, 3, 5 × 10^n) so the axis does not end on an odd label. ECharts does not widen the axis for `markLine` or `markArea` (verified in 6.1.0), hence the `min`/`max` functions. Each threshold shades the region beyond it in its severity color, stacked as a ladder up to the next rule in the same direction, with a dashed line labeled severity and value. A **Fit to data** toggle drops thresholds from the bounds so the axis fits only the visible data; it is a deliberate choice by the user, never the default. Charts use `yAxis.scale: true` and a `dataZoom` slider (preview of the first series, `filterMode: "filter"` so the y axis refits to the window) plus inside zoom on pinch or ctrl + wheel only, so a plain wheel still scrolls the page. The range buttons reset the zoom.
- Table export (`iot-table-tools.js`) skips selection and action columns (blank header, control in header, or `data-export="skip"`).
- **Column sorting is `iot-sort.js`, not simple-datatables** (Sep 2026, `public/js/iot-sort.js`, loaded by the layout). Any `table.is-sortable` sorts by adding a class to the header cell: `sort-alpha` (natural order, "Probe 2" before "Probe 10"), `sort-numeric` (unparseable sorts last) or `sort-custom` (the cell's `data-sort`, numeric when it parses, otherwise natural text). A cell's sort value is its `data-sort`, else its text; blanks always sort last, ties keep the server's order, clicks cycle ascending, descending, server order. It moves rows instead of redrawing them, because simple-datatables redraws the body from its own copy and would write stale values over `live.js` updates. A live update never re-sorts; `live.js` keeps `data-sort` current on value and ago cells. Never on a table simple-datatables runs, and never a copy per page.
- Live updates come from each web process subscribing to the `acct/+/data` feed and relaying over socket.io; the pipeline publishes once. No socket.io adapter is needed across the farm because every instance gets the feed from the broker. Pages update through `data-live` hooks only.
- **socket.io across the farm** relies on ARR's `ITARRAffinity` cookie to keep the long-polling handshake on one server; the connection then upgrades to websocket (101 confirmed through ARR and iisnode, Sep 2026). If intermittent `400 Session ID unknown` responses ever appear, switch the client to `transports: ['websocket']`, which needs no stickiness.
- **Bulk actions share one pattern** (alarms first, devices and gateways Sep 2026), so every list feels the same and the rules live in one place:
  - Selection: a switch in the header (select all, indeterminate when partial) and a switch per row. A sticky `.iot-bulk-bar` appears once one row is checked, with the count, one button per action the user holds the permission for at that location, and "Clear selection".
  - Modal: static backdrop. It names the action and count, collects what the single action needs (comment, reason, minutes), and notes rows skipped because they lack permission or are already in that state. Delete is a plain confirm with a danger button (deletes are soft).
  - Execution: the browser posts one row at a time, in order, to the same endpoint the single action uses. There is no batch endpoint, so permissions, validation and the activity log stay per row. The endpoint answers JSON when asked (`accept: application/json`) with `{ ok, message, state }`, and still redirects for plain form posts. A JSON request for a state the row is already in is refused with 409, never toggled.
  - Progress: the modal stays open with a progress bar, "Action n of N...", and a list of failures. Buttons are disabled until the run ends, then Cancel becomes Close. Rows update in place (`iot-row-pending`, `iot-row-failed`, done state), and a flash summarises "x of N, y failed".
  - Reuse: the bar and modal markup come from `views/partials/bulk-bar.ejs` and `views/partials/bulk-modal.ejs`, and the selection, modal and progress code from `public/js/iot-bulk.js`. Each page supplies only its actions (label, which rows qualify, URL, body, how a row shows the new state) and any extra modal fields. Active alarms, devices and gateways all use it; a new bulk list must too, never a copied page script.

## Auth
- **Opening a password reset link changes nothing** (Sep 2026). Mail scanners and link previews follow links, which used up the single use token before the user clicked. `GET /reset/:token` only peeks and shows a "Yes, reset my password" page; its POST consumes the token and starts the session confined to the set password page (architecture 4.2 otherwise unchanged). The link still expires after `RESET_LINK_MINUTES`. A dead link shows a friendly page that never says why, and logs `password_reset_link_invalid` with the reason (unknown, expired, used or replaced, account deleted) in the activity detail. A visitor who is already signed in never gets the confirm button: both the GET and the POST show a "You are already signed in" page (change password, dashboard, sign out) and leave the token untouched, so the link still works after signing out. Nothing is logged for that case. Alarm action and invite links already render a page on GET and act on POST.
- **API key prefix is a site setting** (Sep 2026), `API_KEY_PREFIX` on Admin > Site settings > API, default `devmon`. This replaces the skill's fixed `iot_` + 32 bytes base62 (architecture 4.5 and 12). Key format is `<API_KEY_PREFIX>_<8 hex>_<24 random bytes base64url>`; only the SHA-256 of the whole key is stored, and authentication looks keys up by that hash, never by parsing the prefix. The prefix must be 1 to 16 URL unreserved characters (`A-Z a-z 0-9 - . _ ~`), checked by `KEY_PREFIX_RE` in `services/apiAuth.js` on save and again when a key is created, because an `.env` value skips the save route. When the prefix is blank or invalid, no key can be created and the account API page shows a warning in place of the Create key form. `key_prefix` stores the visible start (`<prefix>_<8 hex>`, widened to `NVARCHAR(26)` in migration 0018) so the credentials list stays correct after the setting changes; a change affects new keys only.

## Product decisions from the customer
- Docklink SendGrid account is the mail provider; `datatelematics.net` is the authenticated sending domain (`datatelematics.io` has no DNS for mail). From address lives in `MAIL_FROM_ADDRESS`.
- Invites can be resent/renewed; a fresh link invalidates the old one.
- **Add existing users** (Sep 2026, `routes/account/users.js` `/users/search` and `/users/add`, `views/account/users.ejs`). Next to Invite, for anyone holding Manage users on the account. A search box lists matches on name, username or email (2 characters or more, 20 results), and picking one shows the scope and permission picker, capped at the bits the grantor holds as Invite is. The search pool is users who hold a grant on an account the searcher can see or a location the searcher can view (superadmins search everyone; the searcher is left out), so typing addresses never reveals who else is on the server. The add re-checks that pool, so a posted uid from outside it is not found. It creates the grant at once with no email, the difference from Invite, which also grants an existing address directly but by exact email and with an "added" email. A grant that already exists at that scope is refused with a pointer to Edit, never overwritten. Audited as `grant_added`, activity `user_added`.
- **Sensors have their own tags and can opt out of device tags** (Sep 2026). A sensor Tags tab was built and then dropped (fix 8i cancelled); that was a mistake, because single sensors need their own tags (put one sensor on the dashboard without the whole device) and a way to leave one device tag out. The rule, in `combine()` in `services/tags.js` and used through `effectiveForSensor()` everywhere: effective tags = the sensor's own tags, plus the device's tags that the sensor has not excluded. An own tag always applies, even if the same device tag is excluded. Exclusions live in `DTM_tag_exclusions`, not as a flag on `DTM_taggings`, so a reader that forgets them falls back to plain inheritance instead of treating an excluded tag as an own tag. The location dashboard's SQL checks exclusions itself. The sensor Tags tab shows own tags, each device tag with an Inherit switch, and the effective result. Note: device types that set channel `defaultTags` (the server device's `dashboard`) store them on each sensor as own tags, so turning inheritance off does not remove those; remove them from the sensor's own tags.

- **Auto claim membership mode** (Sep 2026, migration 0023, `pipeline/identify.handleBle`, `routes/locations.js`). Deviates from architecture 3.7 ("Hearing is never intent", three modes). A fourth mode, `auto_claim`, for bringing up a site with hundreds of beacons: while it is on, a BLE beacon heard by a gateway placed at that location (live, not archived) whose MAC is on no live device is added there by the system, and the message that claimed it is stored in the same pass. It never moves, archives or takes a device that is live anywhere, so "devices never change location automatically" still holds. Turning it on requires a timeout (1, 4, 12 or 24 hours), stored as `DTM_locations.auto_claim_until_epoch`; when it passes, the location is back to `normal`. The check at claim time is the guard (`auto_claim` with a past end time claims nothing); a leader job sets the mode back to `normal` and audits it. A NULL end time means no timeout: the code honours it, the page does not offer it. No signal floor, on purpose: large locations hear their own beacons weakly. The type is the type module that parsed the advertisement, the name is the type name and the last four of the MAC, and the claim is audited with the system as actor and the hearing gateway. Two locations claiming one MAC at once are settled by `ux_DTM_devices_hardware_id`; the loser relays. BLE only; LoRa nodes have join and commissioning. Changing into or out of it needs the same `lock_location` permission as the other modes. It is a per location setting. Turning it on while another location in the same account has an active auto claim shows a warning naming that location (a beacon goes to whichever location hears it first, so it may land there), and the user can go ahead anyway. For a campus the intended use is one staging location in auto claim, then a bulk move to the buildings.
- **Unclaimed devices, per account** (Sep 2026, migration 0023, `DTM_unclaimed_heard`). The superadmin unknown devices page stays, and each account gets an Unclaimed devices tab, so installers claim without a superadmin. It lists MACs on no live device heard by any gateway in the account, at locations the user can view, and shows every location whose gateways heard each one, strongest signal first. The location filter means heard by any gateway there, not last or best, because a beacon can be heard best, or only, by the building next door. Bulk claim (through `iot-bulk.js`) goes into any location the user picks where they have add permission, not necessarily the filtered one; a wrong one is moved afterwards. `DTM_unclaimed_heard` holds one row per MAC and gateway placement (last heard, last RSSI), written by ingest only while the MAC is unplaced (placed devices have `DTM_device_coverage`), purged by the daily job when not heard for a while. Written for any unplaced MAC a gateway hears, BLE beacons and LoRa frames alike. The location's sub nav has Unclaimed too: the same route and view, filtered to that location. Ignore (migration 0025, `DTM_unclaimed_ignored`) instead of delete, because registry rows are permanent (architecture 3.8) and the MAC is heard again anyway: an account ignore hides the MAC for that account only, and auto claim skips it; a superadmin ignore (account NULL) hides it from the unknown devices page only, never from an account, so a customer can always claim their own beacon. Both pages have Show ignored with Unignore, and bulk ignore and unignore. Ignoring does not stop recording where it is heard, so after Unignore the heard at data is current. Needs the same permission as claiming; audited.
- **Sensor delete and hide** (Sep 2026, `routes/sensors.js`, `pipeline/index.js`). Delete is on the sensor's Settings tab (delete permission, confirm): active alarms cleared, alarm rules and the sensor soft deleted, readings purged after retention, audited, as device delete does for a whole device. A deleted sensor comes back as a new sensor if the device still reports its channel, which is how test and startup data is cleared; this reverses the earlier rule that a removed sensor is never brought back. Keeping a sensor out of sight is Hide instead: a hidden sensor still stores readings, evaluates no alarms (active ones are cleared when it is hidden), and is left out of the device's sensor list, the location dashboard, readings reports, charts (a chart that already has one keeps it in its definition, marked hidden in the editor, but draws no series, so Unhide brings it back) and asset pickers; the device's sensor list has a Show hidden option that lists them with Unhide. Hidden is not disabled: `is_enabled = 0` stops storing readings. The alarm history report still includes hidden sensors on purpose: alarms raised before a sensor was hidden are real events.
