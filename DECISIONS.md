# Voltastc decisions log

Settled decisions and their reasons. Read before changing anything listed; a later change should
add an entry here, not silently reverse one. Architecture reference: the iot-platform skill.

## Origin
- **Voltastc started as a copy of the devmon (DTM) IoT platform** (Sep 2026) and was ported to one Ubuntu server with PostgreSQL. Removed in the port, with their decisions: the IIS farm (iisnode, ARR, `index.js`, `web.config`, deploy scripts), the leader election and migrate application locks, the "every reply is 200" layer and `x-app-status`, SQL Server and every `*.mssql.sql` migration, the `DTM_` table prefix, SendGrid and SMTP mail, the BLE uplink and beacon types (`ble_s5`), BLE auto claim and the `auto_claim` membership mode, MQTT provisioning (`provision/request`), the `dom/` and `dtm/` legacy prefixes, and the `gw7080` and `gateway_generic` type modules. Git history has the old code and the old version of this file.

## Environment and deployment
- **One server:** Ubuntu 26.04 LTS on EC2 (arm64, us-east-2), site `https://app.voltastc.com`, with nginx, the Node app and Mosquitto on the same host and the database on RDS. No load balancer. Deployed Sep 26 2026.
- **pm2 runs exactly one `web` and one `ingest` process** (`ecosystem.config.js`, fork mode, one instance each). There is no election: `services/leader.js` is a stub whose `start()` runs ingest and jobs at once and whose `isLeader()` is true only in the process that called it. "Leader" in comments means the ingest process. Only the ingest process migrates and seeds (behind the 503 "starting" page). A web process that finds pending migrations does not migrate: it reports boot failed (503, and the reason on `/health`) until it is restarted. So a deploy that brings a migration goes through `deploy/install.sh`, which migrates before it reloads pm2; a bare `pm2 reload` after such a pull can leave the site on the 503 page. Anything that notifies, writes alarms or runs on a schedule stays in the ingest process.
- **`deploy/install.sh` installs and re-deploys** (Sep 2026). Run as root from the checkout at `/opt/voltastc`; every step checks first, so a re-run after `git pull` is the deploy: `cd /opt/voltastc && sudo git pull && sudo bash deploy/install.sh`. It stops at the first failing command and names it (`set -E` and an ERR trap), because the first real run ended quietly. Layout: code owned by root (the app cannot change its own code; the installer refuses a checkout the app user cannot read); `.env` root:voltastc 0640; `storage/` owned by voltastc (report files); `certs/rds-global-bundle.pem`; system user `voltastc` with home `/var/lib/voltastc` (pm2 state and logs in `.pm2`, rotated daily by logrotate, 14 kept); broker passwords in `/etc/voltastc/broker.env` (root 0600). The first run asks once for the RDS endpoint, port, database, user and password (never on the command line); `DOMAIN`, `LE_EMAIL`, `CERTBOT_SERVER` and `DB_*` may come from the environment instead. pm2 is started through `env -i`, because pm2 hands the caller's environment to the apps it starts and the installer's shell may hold passwords.
- **pm2 commands as the app user run from a folder it can enter:** `cd /opt/voltastc && sudo runuser -u voltastc -- pm2 ...`. From `/home/ubuntu` (mode 750 on 26.04) pm2 fails with `spawn /usr/bin/node EACCES` and prints a banner as if it were starting a new daemon, which hides the real state. The daemon itself runs under the systemd unit `pm2-voltastc` (`pm2 startup`); on the very first start it logs that no process list was saved yet, which is expected.
- **Node 22 comes from NodeSource** (`node_22.x`, `nodistro`), configured by the installer exactly as NodeSource's `setup_22.x` does (keyring, `nodesource.sources`, pin 600). Ubuntu 26.04's own nodejs is also 22, but its npm package pulls in about 380 more packages (eslint, webpack, babel); NodeSource's nodejs carries npm. unattended-upgrades does not update third party repositories: `sudo apt-get update && sudo apt-get install nodejs`, or a re-run of the installer, picks up Node security releases. pm2 is pinned (7.0.4) and installed with `npm -g`.
- **nginx terminates TLS and proxies to `127.0.0.1:3000`** (`deploy/nginx/voltastc.conf`). Port 80 serves only `/.well-known/acme-challenge/` from `/var/www/letsencrypt` and redirects everything else to the fixed site name (never `$host`); 443 has HTTP/2, websocket upgrade for socket.io, `client_max_body_size 2m` (matches `express.json`), `proxy_read_timeout 120s` and `server_tokens off`. TLS protocols come from Ubuntu's `nginx.conf` (1.2 and 1.3); HSTS comes from helmet. The Ubuntu default site is removed. The installer drops the IPv6 `listen` lines on a kernel with IPv6 turned off, where nginx refuses to start with them.
- **The app listens on `HOST` (default `127.0.0.1`) and trusts only the loopback proxy** (`trust proxy` = `"loopback"` in production). `req.ip` and `req.secure` then come from nginx's `X-Forwarded-For` and `X-Forwarded-Proto`, and a client cannot choose its own address with a forged header, because Express takes the right-most address that is not loopback. Without trust the Secure session cookie is never set and login loops. docker-compose sets `HOST=0.0.0.0` inside its container.
- **One Let's Encrypt certificate serves the web site and the broker** (`certbot certonly --webroot`, renewed by the Ubuntu package's `certbot.timer`). `deploy/certbot-deploy-hook.sh`, installed as `/etc/letsencrypt/renewal-hooks/deploy/voltastc.sh`, ignores other lineages, copies `fullchain.pem` and `privkey.pem` to `/etc/mosquitto/certs` (owner mosquitto, 0600) and reloads Mosquitto and nginx. Mosquitto reloads listener certificates on SIGHUP (2.0.22 `listeners__reload_all_certificates`), so renewals do not disconnect devices (verified). A manual `certbot renew` from a script sleeps up to 8 minutes unless `--no-random-sleep-on-renew` is given.
- **Real HTTP status codes everywhere.** devmon sent every reply as 200 with the real code in `x-app-status`, because the customer's IIS replaced error bodies; with nginx that reason is gone, so `middleware/httpStatus.js` was removed. It had hidden two broken pages (`/locations/:uid/assets` answers 500 because `reasons` is not passed to its view; `/help` is a 404), found in the port and left for later. Client code may branch on `res.ok`.
- **HTTP listens before boot.** Migrations, seeds and settings load after `listen`; until done every request gets 503 "starting" and `/health` reports `starting` / `boot failed` with the reason. Unhandled rejections are logged, not fatal. An ingest process whose boot fails exits so pm2 restarts it.
- **`.env` is never committed** (reverses devmon, whose customer kept production values in the repository). `.env` and `.env.*` are gitignored and `.env.example` is the template; the installer fills `APP_URL`, `SESSION_SECRET`, `SETTINGS_KEY` and the database lines. Only connection details and secrets live there; everything else is a site setting. `config/env.js` passes `DOTENV_CONFIG_PATH` to `dotenv.config()` (which ignores the variable on its own), so docker dev reads `.env.local` and nothing falls through from `.env`.
- **The superadmin is seeded from `.env`:** `SEED_SUPERADMIN_USERNAME` (`jseese`) and `SEED_SUPERADMIN_EMAIL` (`jeff@goseese.com`) are in `.env.example`; `SEED_SUPERADMIN_PASSWORD` is optional and only ever in the real `.env`. Blank prints a random one time password once, from `npm run seed` or the installer (never into the pm2 logs, because the installer seeds before pm2 starts). Created only when no live user has that email; the account is confined to the set password page until a new password is saved.
- Static assets carry `?v=<commit or boot time>`; production caches them 7 days. The commit comes from `public/build-info.json`, then `build.json`, `GIT_COMMIT`, or the checkout's `.git` (what the server uses, since it deploys by `git pull`). The footer shows version and uptime.
- `/health` is unauthenticated on purpose (quick "did my deploy land"); it returns version, commit, boot time, host name, process id and whether that process runs ingest.

## Mail, SMS and branding
- **Mail is Amazon SES only** (`services/mail/ses.js`, `@aws-sdk/client-sesv2` SendEmail). No AWS keys in the app: the SDK's default credential chain uses the EC2 instance role, which needs `ses:SendEmail` on the verified identity; a `~/.aws` profile works for dev. One setting, `SES_REGION`. `MAIL_DRIVER` seeds as `none`, which records `suppressed` and logs the mail. SES is not set up yet (Sep 2026) and stays database configuration: set `MAIL_DRIVER=ses`, `SES_REGION` and `MAIL_FROM_ADDRESS` in Admin > Email and give the instance role the permission; no redeploy. Until then password reset and invite emails are not delivered.
- Mail and SMS providers are drivers that declare their own settings, grouped into their tabs. Every send writes a `notifications` row first, then the outcome, the message body and the provider's raw answer. A failure is recorded as `"ErrorName: message"`. `mail.send` takes one address or a list for `to` (a list is one message with every address in To; the notifications row stores them comma separated) and an optional `replyTo` address or list (SES `ReplyToAddresses`, checked in the SDK types).
- **SMS is hidden, not removed** (Sep 2026). The code, the `services/sms` drivers and the schema columns stay. No phone number can be entered anywhere (profile, contacts), `users.sms_enabled` keeps its default false and is never taken from a form, alarm rule channels show no SMS column, there is no Admin SMS tab, and `SMS_DRIVER` stays at its seeded `none`. Contacts are email only.
- **The site name is the `SITE_NAME` setting** (seeded `Voltastc`), read only through `config/settings.siteName()`, which falls back to `Voltastc`. Every page title, email, alert, report and invite uses it; nothing else may hard code the name. The mail From name is `MAIL_FROM_NAME`, else `siteName()`.
- Identifiers: package `voltastc`, session cookie `voltastc.sid`, `API_KEY_PREFIX` seed `voltastc`, webhook headers `X-Voltastc-Signature`, `X-Voltastc-Event`, `X-Voltastc-Delivery`, dynsec command correlation ids prefixed `voltastc-`. Internal JavaScript names such as `window.devmonChart` are not visible and were left.
- Branding: `public/img/icon.png` is the favicon and the collapsed sidebar mark; `public/img/site_logo.png` is on the sign in card and in the sidebar. Theme green `#53b036` (`--iot-primary`, `--iot-active`), hover `#6cc451`, nav active background `#182a1b`.

## Database (PostgreSQL)
- **PostgreSQL on RDS, version 15 or newer** (production runs 18.3). The baseline uses `NULLS NOT DISTINCT` (15+). RDS forces SSL, and the app verifies the server certificate against the RDS global CA bundle (`DB_SSL_CA`, downloaded by the installer); `db/knex.js` refuses to start with `DB_SSL` on and no CA file. The first migrate runs `CREATE EXTENSION citext`, which needs the RDS master user or `rds_superuser`, so the app currently connects as the master user. If the master password is ever managed by Secrets Manager, RDS rotates it every 7 days and `.env` goes stale; keep it self managed, or give the app its own login.
- **Migrations are plain `NNNN_name.sql` files**, each run in one transaction as a single multi statement query (simple protocol). `pg_advisory_xact_lock(1450142836)` guards both the `schema_migrations` CREATE TABLE IF NOT EXISTS (not race safe on its own; reproduced) and each file, which re-checks that it is not already applied. knex rewrites every `?` to `$n` even without bindings, so a literal `?` in a migration is written `\?`. No `CREATE INDEX CONCURRENTLY` (it cannot run in a transaction).
- **The baseline is closed; every schema change is a new migration** (Jeff, Sep 26 2026). The production database was created with `0001_baseline.sql` applied and seeded, so editing the baseline in place would never reach it. Dropping and recreating the database while it held only seed data was considered and rejected: new migrations are the long term habit anyway. The event log (`event_log` replacing `activity_log`) is therefore `0002`.
- **No table prefix.** devmon's `DTM_` prefix is gone; `T()` in `db/knex.js` is a pass through kept so every query still goes through one place. Index names lost the prefix too (`ux_devices_hardware_id`, `ux_sensors_channel`).
- **Case insensitivity is CITEXT** on `users.username`, `users.email`, `username_history.old_username`, `invites.email`, `invites.username`, `contacts.email` and `tags.name` (each with a CHECK for the old length), replacing SQL Server's case insensitive collation. Everything else is case sensitive; searches use `ilike`, with `%`, `_` and `\` escaped in user input.
- **Postgres aborts a transaction on any error** (SQL Server did not). A duplicate is caught with `isUniqueViolation(err)` (`err.code === "23505"`), and inside `knex.transaction` a caught error must not be followed by another statement on that transaction; use a savepoint (`trx.transaction`) if one is ever needed. Autocommit catches are fine.
- Booleans are `BOOLEAN` (compare with `false`, not `0`). Epoch columns are `BIGINT` seconds.
- `insertId()` normalises `.returning()` results; `notFoundError()` is the only way to deny (denied and missing look identical).
- **Malformed ids are not found** (Sep 2026, `middleware/account.js` `isUuid`, `uidParam`, `intParam`). Postgres refuses to compare a UUID or integer column with text that is not one (error 22P02), so `/devices/xyz` and the like ended as a 500 where SQL Server's looser comparison had hidden it. Every router that takes ids in its paths checks them first with `router.param` (`uid`, `ruleUid`, `id`, `runId`, `grantId`), ids posted in forms are checked before their lookup, and the API rejects a malformed sensor id as that one reading, not the whole request. A malformed id is the same plain 404 as a missing row. Mapping 22P02 to 404 in the error handler was rejected: it would also hide real bugs as 404s. A new route with an id in its path adds its `router.param` line.
- Settings: an `.env` key of the same name overrides the database and shows read only in the UI. Secrets are AES-256-GCM with `SETTINGS_KEY`; never rotate it once anything is encrypted.
- **`devices.hardware_id`**, `VARCHAR(255) NULL`: the string that identifies the hardware (MAC for radio kinds, host name or IMEI for direct devices), never an FK and never the display name. Unique among live, unarchived rows (`ux_devices_hardware_id`), global not per location; archived and deleted rows keep theirs. The `platform_server` device's id is `new URL(APP_URL).hostname`; its seed and the server stats job look it up by hardware id, never by name.
- **Sensor description:** `sensors.description TEXT NULL`, where NULL inherits the device type channel's optional `description`. Edited in place on the sensor Overview; saving the default text unchanged, or empty, stores NULL, so later changes to a type's description still reach sensors that never customised it.
- Location `alarm_mode` is `active | muted | offline`. Muted evaluates and records but notifies nobody; offline evaluates nothing and clears active alarms when set. `notifications_muted` is kept in sync as the notification gate.

## MQTT and broker
- **MQTT topics live in `mqtt/topics.js`** and nowhere else. Device uplinks: `dev/{guid}/frame` (one relayed node frame), `status` (connectivity, the connect message retained, LWT `{"online":false}`), `data` (the device's own readings, not retained), `config/{key}` (one config value per publish, not retained), `geoscan` (not retained) and `cmd_ack` (the device heard a command). Downlink: everything the server sends a device is at or under `dev/{guid}/cmd`, and ACLs scope the subtree `dev/{guid}/cmd/#`, which also matches the bare topic, so a new command topic needs no ACL change. `acct/{account_guid}/#` is server published. `con/endpoint` is the retained provisioning URL. Nothing else is accepted.
- **The broker is Mosquitto 2.0.22 from Ubuntu 26.04 on the same server**, with dynamic security as the only authentication source, `allow_anonymous false`, 1883 on `127.0.0.1` for the local Node processes, 8883 TLS for devices, and persistence on. The Mosquitto PPA builds 2.1.2 for 24.04 only; the app works the same on both (verified against both sources). Users, roles, the AppArmor rule and the reasons are in `dynsec-broker-summary.md`. Back up `/var/lib/mosquitto/dynamic-security.json` and `/etc/voltastc/broker.env`.
- **The app's broker logins:** `voltastc_server` (role `voltastc-server`) for the ingest client and the web process's realtime relay; `voltastc_dynsec` (role `dynsec-admin`) for creating and removing device users; `announce` for first contact. `scripts/broker-bootstrap.js` creates and verifies them, and with `--settings` stores the MQTT site settings.
- **MQTT client ids:** the ingest client uses `MQTT_CLIENT_ID` (blank falls back to `server-<APP_URL host>`; the installer stores `voltastc-server`) with a persistent session. The realtime relay uses `<MQTT_CLIENT_ID>-web-<host>-<pid>` and the dynsec driver `<MQTT_CLIENT_ID>-dynsec-<host>-<pid>`, both with a clean session, so no process can evict another. Two connections with the same client id kick each other off the broker regardless of username.
- **MQTT connection settings live in site settings** (Admin > Site settings > MQTT): `MQTT_HOST`, `MQTT_PORT`, `MQTT_TLS`, `MQTT_USER`, `MQTT_PASSWORD` (secret), `MQTT_CLIENT_ID`, `BROKER_DRIVER`, `MQTT_DYNSEC_USER`, `MQTT_DYNSEC_PASSWORD` (secret), `PROVISION_PATH`, `PROVISION_RATE_PER_MINUTE`, read only through `mqtt/broker.js`. On this server the app connects to `127.0.0.1:1883` without TLS. Changes apply without a restart: each process polls the newest `updated_epoch` of the mqtt rows every 15 s (`mqtt/watch.js`) and reconnects its clients. A blank `MQTT_HOST` leaves ingest and the relay unconnected with a warning.
- **Device provisioning is an unauthenticated router at `/provision/v1`, not part of the API.** `routes/api.js` puts `apiAuth.authenticate` on its whole router, so a device on first contact, holding no key, would be refused before reaching a handler. `routes/provision.js` is mounted above `/api/v1`, ahead of session and CSRF, answers JSON for every path under its mount and carries its own error handler (`middleware/errors.js` renders HTML outside `/api/`). Rate limited per client IP by `PROVISION_RATE_PER_MINUTE` (default 10) with an in process bucket dropped whole each minute. Issuing is `services/provisioning.issue()`.
- **Firmware contract, real HTTP status codes:** 200 with `password`, store it; 200 with `existing: true`, keep yours; 400 bad request, do not retry; 409 another request is issuing this unit, retry in seconds; 429 retry after `retry_after_secs`; 500 retry with backoff. Error bodies are `{ error, ... }`. Allow about 20 s per request. On `existing` with MQTT logins that keep failing, back off: that is lost flash or a broken account, and the fix is Reprovision. The device side is `device-provisioning.md`.
- **First contact runs over a retained `con/endpoint` message** (`services/connectEndpoint.js`). Firmware carries the broker host only and learns the provisioning URL from a retained message it reads as the shared `announce` user, whose role can read that one literal topic and nothing else. Payload `{ url, published }`; the date is for a human with `mosquitto_sub`, firmware ignores it. The path is the `PROVISION_PATH` setting, the host always comes from `APP_URL` (`mqtt/broker.provisionUrl()`). Published by the ingest process on every ingest connect and once a day (`jobs/tasks/connectEndpoint.js`).
- **The dynsec driver may run in any process** (`services/broker/dynsec.js`), each with its own client id and a clean session. Facts, verified in the 2.0.22 and 2.1.2 sources: success is the absence of an `error` key; replies go to every subscriber of the response topic with a NULL client at QoS 0, so correlation is mandatory and a reply can be lost, hence a 10 s timeout on every command and idempotent operations; a failing command does not abort its batch. Tolerated errors are exactly `Role already exists` (then `modifyRole`, which replaces the ACL set and repairs a stale role), `Client already exists` (then `setClientPassword`), `Client not found` and `Role not found` on delete. Every create reads the role back with `getRole` and throws if an ACL is missing.
- **Credentials are issued synchronously** (`services/provisioning.issue()`). The broker account is created before the row is activated, so a device is never handed a password for an account that does not exist. The claim is the INSERT of the new credential row on first contact (the unique MAC index lets one request win) or one conditional update from `pending` to a transient `issuing` (a claim older than 60 s counts as abandoned). The claim exists because the broker round trips make the request slow enough for a firmware retry to overlap its first attempt; without it both would set different passwords. A broker failure returns the row to `pending` and reaches the device as a 500; a lost reply is safe because the retry hits "already exists".
- **Device ACLs keep subscribe and receive together** (`mqtt/topics.deviceAcls()`). The broker's default `publishClientReceive` is deny, so a role with a subscribe ACL and no receive ACL lets a device subscribe, be granted its QoS, and then silently never receive a command. Both come from one loop over `DOWNLINK_TOPICS`; add a downlink topic there, never push a single ACL by hand. Role ACL types must be the specific ones (`subscribePattern`, `subscribeLiteral` and so on); plain `subscribe` and `unsubscribe` are only valid for `setDefaultACLAccess`.
- **Uplinks are split by purpose.** `status` is connectivity only: the connect message retained, other status publishes not retained, LWT `{"online":false}`. Readings go to `data` and are never retained, because readings are a time series and a retained topic holds current state. Config is deliberately not retained, so a broker restart does not replay every unit's configuration; the unit sends it on connect. The firmware version key is `firmware` (`fw` also accepted). Config and geoscan are accepted and logged at debug; storage and the location lookup are not built. A unit provisioned before an ACL change keeps its old role until Reprovision, and the daily broker audit flags it until then.
- **Retained replays never count as contact** (`mqtt/client.js`, `pipeline/identify.js`). Every reconnect of the ingest client re-subscribes, and the broker then re-sends every matching retained message with the retain flag set. A retained status only refreshes the firmware version, never last seen, readings or the registry.
- **`cmd_ack` is an uplink:** firmware publishes `dev/{guid}/cmd_ack` when it hears a command. Logged by ingest for now, for the Commands tab later.
- **Gateway config is kept per unit, written without retained messages** (`unit_config`, `services/unitConfig.js`, `/devices/:uid/config`). One row per MAC and key: `reported_*` from `dev/{guid}/config/{key}`, `desired_*` for a write the unit has not confirmed. A write publishes `dev/{guid}/cmd/set_config/{key}` with the bare value, QoS 1, not retained; the unit saves it and publishes `config/{key}` with the value it now holds, and a match clears the pending state. Retained was rejected: clearing a retained message is a zero byte publish every subscriber receives. A unit that was offline gets every pending write again when ingest sees its live connect message, and the page can cancel a pending write. Both sides are compared after `services/configValues.normalize()`. Which keys exist, their kind, and whether they are writable, advanced or need a confirm live only in the type module's `configKeys`, with `maxLength`, `min` and `max` from the firmware's own limits, because firmware that truncates or wraps a value would never echo a match. Publishing goes through `mqtt/downlink.js`, which uses the ingest client in the ingest process and the realtime relay's connection in the web process.
- **The config page updates live from a notice, never from values** (`services/unitConfig.notify`, `realtime/index.js`, `views/devices/config.ejs`). A change to a unit's config rows publishes `acct/{account}/config` with `{ event: "config", device }`; the web process relays it to the account's socket.io room, and the page fetches `GET /devices/:uid/config/rows` (same permission checks as the page). Values never go over the socket or MQTT, because the account room reaches every member of the account and config holds WiFi passwords. The fetch is debounced one second, a row being edited is left alone, and a response with no rows (an expired session) is ignored. The row markup lives only in `views/devices/config-rows.ejs`.
- **Incoming messages never change a device's offline state.** `is_offline` is set with intent by a person (device Settings) or a scheduled offline period (`jobs/tasks/offlinePeriods.js`), and only those change it; a device that goes up and down while being worked on stays offline for the whole period.
- **A daily audit checks the broker against the database** (`jobs/tasks/brokerAudit.js`). One verbose `listRoles` returns every role with its ACLs; each unit holding its own account is checked for its `dev-{guid}` role and every ACL `deviceAcls()` produces. The result goes in `broker_fault` and `broker_checked_epoch` and shows as a banner on the device page of the unit's current placement, pointing at Reprovision. Detect only, by choice. `issue()` and `reset()` clear the fault.
- **Broker identity belongs to the unit, not the placement.** A **unit** is one physical piece of hardware keyed by MAC: its `device_credentials` row holds the broker username (a GUID, the one in `dev/{guid}/...`), the password and the state, and lives across placements. A **placement** is a `devices` row, one stint at one location, owning sensors, history and alarms. A unit's current placement is not stored: it is the one live, unarchived device row holding its MAC (`ux_devices_hardware_id` allows one). Consequences, all deliberate:
  - **Every unit gets credentials on first contact**, placed or not, so firmware can be flashed, provisioned and shipped. `POST /provision/v1` takes `{ hw, model, fw }`; `model` is required and decides the device type (the module whose `models` list contains it, exact match, `deviceTypes.forModel()`), which must be of kind gateway or direct, never `platform_server`, else 400. A new product needs its model string added to a type module before its units can provision. The endpoint confirms that a MAC is a unit and returns its GUID to any caller; accepted, because the GUID is the broker username and appears in every topic. The password is never re-sent.
  - **Adding a device creates no credential;** a unit that already holds credentials starts delivering to its new placement at once.
  - **Archive, delete and location delete leave the unit alone.** Its credentials keep working and it stays connected; its data is dropped because there is no placement. Ingest resolves topic GUID to unit to current placement and logs unclaimed traffic at debug.
  - **Revoking is Reprovision** (`provisioning.resetUnit(mac)`): deletes the broker account and flips the unit to pending; the next request gets a fresh password under the same GUID. On the device settings page for placed units and on Admin > Unknown devices for unclaimed ones.
  - **`device_credentials.device_id` is dead:** nullable, never written, never joined. Look a unit up by MAC or by `broker_username`.
  - **Unclaimed units that never connect are cleaned up** (`jobs/tasks/unitCleanup.js`, daily): issued more than 30 days ago with `mqtt_seen_epoch` still NULL, the broker account is deleted and the credential soft deleted. The registry row stays. The endpoint being unauthenticated means anyone can mint units for made up MACs; each is confined to its own topic tree by its ACLs, and the cleanup bounds how many accumulate.

## Devices, sensors and alarms
- **Sensors are created on first value, not when a device is added** (`pipeline/index.js`, `services/devices.createSensor`). Deviates from architecture 3.2. A usable value (a finite number or a boolean) for a channel the type declares, on a device with no live sensor for it, creates the sensor in its own transaction and is stored in the same pass. A device therefore only has the sensors it actually reports, and a channel added to a type later appears with its first value. Two writers racing on one channel are settled by `ux_sensors_channel`; the loser re-reads.
- **Default alarms are declared per channel, and there is no default no-data rule** (`services/devices.createSensor`, validated in `deviceTypes/index.js`). A channel's `defaultAlarms` holds threshold entries and `{ rule: "no_data", timeoutSecs, severity? }` entries; a channel with none gets no alarm rules. `validate()` refuses a module that still carries the old type or channel level `noDataTimeoutSecs`. `platform_server` appends a no-data entry to each of its channels. Pod types will have no default alarms.
- **Channel naming standard** (enforced in `deviceTypes/index.js`). A channel id says what the reading is in terms that fit every device, lower case words joined by hyphens: `int-vbat` the device's own battery (V), `int-vbat-pct` its percent, `vin` external power in, `int-temp` / `int-humidity` board mounted, `ext-temp-1..n`, `ext-sw-1..n`, `pir-motion`, `acc-x|y|z`, `cycles`, `run-time`, the device's own radio raw as `csq` or `wifi-rssi` and as a percent `signal`, and what a hearing gateway measures per gateway (`rssi-xx:xx`, `signal-xx:xx`, `heard-count-xx:xx`). Pick the global name before adding a new kind of sensor, and add it to this list. The firmware's own payload keys never change: the type's `dataMap` or parser maps them to the standard ids. `platform_server` predates this and sets `legacyChannelIds: true`.
- **Per gateway sensors** (`deviceTypes/index.js` `gatewayChannelId`, `gatewayValues`, `channelDef`). What a gateway measures about a device it hears (RSSI, heard count) is one sensor per hearing gateway: a channel declared `perGateway: true` is stored as `{id}-{last two bytes of the gateway MAC, lower case}` and named `{name} {XX:XX}`. One mixed sensor was rejected: readings from several gateways on one chart are meaningless. The sensor follows the gateway's hardware, so a replaced gateway starts new sensors. This is how a controller pod will report what it hears from its target pods.
- **Battery and signal percent** (`services/levels.js`, `pipeline/levels.addLevels`). Ported from the legacy PHP helpers, interpolation unchanged (1..100, clamped). `int-vbat-pct` comes from `int-vbat` and the battery chemistry (the device's `battery_chemistry`, else the type's `batteryChemistry`). A channel declaring `signal: "lora"|"ble"|"csq"|"wifi"` gives `signal` with the same per gateway suffix. Computed before sensors are created and stored as ordinary readings, only for channels the type declares, never over a value the message carries. `li_ion` is PROVISIONAL (a generic 3.7 V cell curve) until measured; `wifi` is a linear -50 dBm 100 to -100 dBm 0.
- **Device commands are declared by the type and gated per command** (`deviceTypes/*.commands`, `routes/devices.js`, `views/devices/commands.ejs`). Each command publishes to `dev/{guid}/cmd/{name}` with the firmware's own name, so the `cmd/#` ACL covers it. Each names its own permission bit (a harmless "report now" needs `view`; reboot, join or firmware need `edit` and set `confirm`); the tab shows only commands the user holds the bit for, and the POST checks again. Commands are sent now and never queued or retained: a reboot arriving hours later on reconnect would be a surprise. `cooldownSecs` limits sends per device across users.
- **Sensor delete and hide** (`routes/sensors.js`, `pipeline/index.js`). Delete (delete permission, confirm) clears active alarms, soft deletes the rules and the sensor and purges readings after retention; a deleted sensor comes back as a new sensor if the device still reports its channel, which is how test data is cleared. Hide keeps storing readings but evaluates no alarms and leaves the sensor out of the device list, the location dashboard, readings reports, charts and pickers, with Show hidden and Unhide on the device's sensor list. `is_enabled = false` is different: it stops storing readings. The alarm history report still includes hidden sensors.
- **Unclaimed devices, per account** (`unclaimed_heard`, `unclaimed_ignored`). Each account has an Unclaimed devices tab, so installers claim without a superadmin: MACs on no live device heard by any gateway in the account, at locations the user can view, with every location whose gateways heard each one, strongest signal first. Bulk claim goes into any location the user picks where they have add permission. `unclaimed_heard` holds one row per MAC and gateway placement, written by ingest only while the MAC is unplaced, purged when not heard for a while. Ignore instead of delete, because registry rows are permanent (architecture 3.8): an account ignore hides the MAC for that account only; a superadmin ignore (account NULL) hides it from the unknown devices page only. Ignoring does not stop recording where it is heard.

## Navigation and UI
- **Location first.** `/locations/<uid>` is the location dashboard; the sidebar Monitor section exists only while inside a location and every link carries the uid (shareable support links). Analytics and Reports are account wide, under Manage.
- **Every page rebuilds from its URL; the session holds no navigation state** (`middleware/account.js`, `routes/account/index.js`, `nav/menu.js`). `/account` always lists the accounts the user can view; each account's pages live under `/account/<account uid>/`, and `loadAccount` checks the uid against the user's visible accounts (anything else is `notFoundError()`). A detail page needs only its own uid (`/locations/<uid>`, `/devices/<uid>`, `/sensors/<uid>`, `/alarms/<uid>`, `/analytics/charts/<uid>`, `/analytics/dashboards/<uid>`, `/reports/<uid>`); the account and location come from the row, and a row whose account the user cannot view is not found. Old paths redirect to `/account`.
- The location's Assets page is hidden from the left nav (commented out in `nav/menu.js`, may come back); its route and view stay, and it needs `reasons` passed from `routes/locations.js` before it renders.
- Breadcrumbs are `Account / Location / ...`, built by `nav/breadcrumb.js` (tested), resolved at render time from `req.originalUrl`.
- Inline page scripts must run on `DOMContentLoaded`: vendor libraries load at the end of the body.
- Theme variables everywhere; Bootstrap `bg-body-tertiary`, `text-bg-light` and simple-datatables' own chrome are overridden in `iot-theme.css` because they paint light on the dark theme.
- Relative time labels carry `data-epoch`, tick every 30 s in `live.js`, and show a browser-local timestamp on hover (`.iot-hint` for any element with details in its `title`).
- **Charts always show alarm thresholds by default** (`views/sensors/show.ejs`). The y axis spans the visible data plus every enabled threshold, with a 5% margin and bounds rounded to ECharts' tick steps (ECharts does not widen the axis for `markLine` or `markArea`, verified in 6.1.0). Each threshold shades the region beyond it in its severity color. **Fit to data** is a deliberate toggle, never the default. `dataZoom` slider plus inside zoom on pinch or ctrl + wheel only.
- Table export (`iot-table-tools.js`) skips selection and action columns.
- **Column sorting is `iot-sort.js`, not simple-datatables** (`table.is-sortable`, header classes `sort-alpha`, `sort-numeric`, `sort-custom`, value from `data-sort` else the text). It moves rows instead of redrawing them, so `live.js` updates are never overwritten; a live update never re-sorts.
- **Live updates:** the web process subscribes to `acct/+/data` and relays over socket.io; the pipeline publishes once. Pages update through `data-live` hooks only. Through nginx the connection upgrades to websocket (101 verified).
- **Bulk actions share one pattern** (`views/partials/bulk-bar.ejs`, `views/partials/bulk-modal.ejs`, `public/js/iot-bulk.js`): header and row switches, a sticky bar with the count and one button per permitted action, a modal that names the action and notes skipped rows, then one POST per row, in order, to the same endpoint the single action uses (no batch endpoint, so permissions, validation and the event log stay per row). The endpoint answers `{ ok, message, state }` when asked for JSON and refuses with 409 a request for a state the row is already in. A new bulk list must reuse these, never a copied page script.

## Auth
- **Opening a password reset link changes nothing.** Mail scanners and link previews follow links, which used up the single use token before the user clicked. `GET /reset/:token` only shows a "Yes, reset my password" page; its POST consumes the token. A dead link shows a friendly page that never says why and logs the reason. A signed in visitor never gets the confirm button and the token stays unused.
- **API key prefix is a site setting**, `API_KEY_PREFIX` (Admin > Site settings > API, seeded `voltastc`). Key format `<API_KEY_PREFIX>_<8 hex>_<24 random bytes base64url>`; only the SHA-256 of the whole key is stored and keys are looked up by that hash. The prefix must be 1 to 16 URL unreserved characters, checked on save and when a key is created. `key_prefix VARCHAR(26)` stores the visible start, so the list stays correct after the setting changes.

## Accounts and users
- Invites can be resent or renewed; a fresh link invalidates the old one.
- **Add existing users** (`routes/account/users.js` `/users/search` and `/users/add`). Next to Invite, for anyone holding Manage users on the account: search (2 characters or more, 20 results, `ilike` with escaped input) among users who hold a grant on an account the searcher can see or a location the searcher can view (superadmins search everyone), then the scope and permission picker, capped at the grantor's own bits. The add re-checks that pool and creates the grant at once with no email. An existing grant at that scope is refused with a pointer to Edit.
- **Sensors have their own tags and can opt out of device tags** (`combine()` in `services/tags.js`, `effectiveForSensor()`): effective tags are the sensor's own tags plus the device's tags the sensor has not excluded. Exclusions live in `tag_exclusions`, so a reader that forgets them falls back to plain inheritance. Channel `defaultTags` are stored on each sensor as own tags.

## Event log
- **One `event_log` table replaces `activity_log`** (migration 0002, Sep 2026), following Jeff's event log README (the hello_wappler and Docklink design). Columns are what the viewer filters on: `time` (epoch ms), `user_id`, `api_credential_id` (API keys are their own identity here), `account_id`, `channel` (`web`, `ajax`, `api`, `device`, `job`, `mqtt`), `event`, `correlation_id`; everything else is in `details` (JSONB). Sort by `time`, with `id` as the tiebreaker (inserts are not awaited, so id order can differ from event order). No foreign keys: a log row outlives what it names. Purged daily after `EVENT_LOG_DAYS` (default 30; the old `ACTIVITY_LOG_DAYS` value carries over). Kept separate, because their lifetimes or jobs differ: `audit_log` (permanent field level history), `notifications` (365 days, the notification detail view), `webhook_deliveries` (retry state), `raw_publish_log` (optional raw MQTT capture).
- **Every request writes a `request` row when it starts and a `request_end` row when it finishes** (`middleware/eventLog.js`), never awaited, both with `req.id` as the correlation id, the same id sent as `x-request-id` and shown as the reference on error pages, so a user's reference number opens their request. The start row holds method, path, query, redacted body, ip and user agent; the end row status and duration (`aborted` when the client went away first). Two mounts: before `/provision/v1` and `/api/v1` for those paths (channel `device` or `api`; the API key id lands on the end row), and right after the session, before CSRF, for everything else, so the start row already knows the user and CSRF refusals are logged. A web end row takes the user from the session as it stands after the request, so a login shows the user on its end row and a logout on its start row. Channel: `ajax` for XHR, a JSON Accept header, or a `Sec-Fetch-Dest` other than document (the only way to tell a plain `fetch()` from a page load), else `web`.
- **Never stored:** any field named like pass, secret, token or csrf, and `current` (the current password), at any depth; the `value` of a site setting save or a device config write (secret settings and WiFi passwords post under that plain name); the token in `/reset/`, `/invite/` and `/a/` links (stored as `[token]`). Details over 8 KB lose the body, then the query, keeping only their size. Not logged at all: `/admin/logs` itself, `/health`, the sidebar alarm badge poll (every open page, every 30 s), the config rows refresh, and asset 404s.
- **Handler events keep the old call shape:** `services/activity.log(req, action, fields)`, so its call sites did not change; the actor goes in `user_id` or `api_credential_id`, the rest (actor name, ip, user agent, outcome, entity, detail) in `details`, with the request's correlation id. `record(action, fields, ctx)` is for work without a request (jobs, provisioning), with its own channel and correlation id. Security events are awaited by their callers, so the login lockout (`login_failed` by name and by ip in the window) and the device command cooldown (`device_command` by entity and name) always see the previous row; both are queries on `(event, time)` plus a `details->>` filter.
- **Jobs and ingest write no row per MQTT message or per job run**, which would be one row per reading. They record only the events that were already logged (unit provisioned, unit cleanup), each run or request with one correlation id.
- **Viewer:** Admin > Event log (`/admin/logs`), superadmin only. Filters are GET parameters, so a filtered view is a shareable link: period (last 1 h, 24 h, 7 d or 30 d), user or API key, account, event (suggestions from the last 7 days), channel, request id, errors only (`request_end` with status 400 or more). Newest 500 first, with an Older link keyed on `(time, id)` so rows sharing a millisecond are never skipped (tested with 1200). A request id shows every row of that request, oldest first; each row's summary expands to its details. Times are shown in the browser's time zone, to the millisecond.
- **Live view:** socket.io namespace `/admin-logs`, checked at the handshake against the session (superadmin, not deleted, not confined to the set password page; anyone else gets `forbidden`). `db/repos/events.insert` emits each row before inserting it, so the live view works even if the insert fails. Only the web process has a socket server, so ingest and job rows appear on the next page load (Jeff, Sep 2026). The page adds live rows through the same filters as the table (not the period), builds them with DOM calls so nothing in a row can inject markup (verified with a hostile path), and keeps at most 1000 rows. Live is on for the first page and off when viewing one request or an older page.

## Support requests
- **The conversation lives in the app** (Jeff, Sep 2026; migration 0003, `services/support.js`, `routes/support.js`). `support_requests` (uid, requester, optional account, subject, status, created, updated and closed times) and `support_messages` (author, body up to 10000 characters, time, `from_support`). A request is reached by `/support/<uid>`, visible to its requester and to superadmins only; anyone else gets the same 404 as a missing request. Every reply is typed there; email only says there is something to read.
- **Status:** `open` (needs a support answer: new, or the requester replied, including to a closed request, which reopens it), `waiting` (support answered), `closed` (by a superadmin, who can also reopen). Only superadmins close. A superadmin answering someone else's request writes as support; on their own request they are the requester.
- **Email:** a new request or a requester reply goes to `SUPPORT_EMAILS` (Admin > Site settings > Email, comma separated; Jeff may add a Teams channel address) as ONE message with every address in To and Reply-To set to the same list, with the full text and the link. The requester is never a recipient or the Reply-To of that mail, so a reply all stays inside the team and is not recorded. A support reply emails the requester the text and the link, saying email replies are not read. Mail failures (SES not set up) are recorded in `notifications` and never undo the request. An empty `SUPPORT_EMAILS` logs a warning.
- **Pages:** `/help` (was a 404) has the intro, the request form (an account picker only when the user can see more than one account; with exactly one it is filled in) and the user's own requests. The profile has Details and Support tabs (`/profile/support`). Superadmins get "Support requests" (`/support`) under Support in the left nav, tabs Needs answer, Waiting on requester, Closed, All, and a badge counting `open` requests, computed once per page load for superadmins (one indexed count, no polling). The conversation page shows the requester's name, email, username and account to superadmins, and Close or Reopen. Events: `support_request_created`, `support_reply` (from support or requester), `support_closed`, `support_reopened`.

## Pod stations
- **Device types** (Jeff, Sep 2026): `controller_pod` (model `vpod-ctl`, kind gateway, runs a station), `account_pod` (`vpod-acct`, kind gateway), `target_accel` (`vpod-acc`, "Target pod, impact") and `target_tof` (`vpod-tof`, "Target pod, laser"), both kind node. Controllers and account pods provision and log in like any gateway; target pods never hold broker credentials, so provisioning refuses their models. Every pod runs on 12 V with the same 4.2 V Li-Ion backup as the standard gateway (`deviceTypes/shared/pod.js` holds the shared readings: power in, battery, charge state, board temperature and humidity, run time, free heap). Target types list the station types they pair with in `pairsWith`; a station type sets `station: true`.
- **Radio:** target pods talk to their controller over ESP-NOW, unencrypted, with each pod checking the sender's MAC in software (Espressif: at most 20 peers, 17 of them encrypted; unencrypted unicast is accepted from anyone). About 15 target pods per controller is the plan; the peer table allows about 19 plus the broadcast entry. Every pod must be on the controller's WiFi channel. The ESP-NOW firmware readme is written when firmware work starts.
- **Relay frames are JSON** on `dev/{guid}/frame`: `{ mac, rssi, model, fw, boot, seq, data: { ... } }`, `data` keyed like the type's `dataMap` (e.g. `vin`, `vbat`, `charge_state`, `int_temp`). Binary frames still work for other types. Dedup counter: `boot * 2^32 + seq`, where `boot` is the pod's boot count kept in NVS and incremented at every boot, because `seq` restarts at boot while `device_frames` keeps counters for 24 hours; without `boot` the counter is `seq` alone and a reboot's frames are dropped as duplicates until `seq` passes the old value. A frame with no `seq` is not deduplicated. The controller's RSSI for each pod is kept per controller (`rssi-xx:xx` and `signal-xx:xx` sensors on the pod) and shows in the station roster.
- **A controller's page is about its station** (Jeff): its first tab, Station (`/devices/<uid>`), shows the status, last seen, type and hardware id cards and the station panel, nothing else. Its Sensors tab (`/devices/<uid>/sensors`) is the sensors table only. It has no coverage table: only its own target pods can be heard by it. Other types, target pods included, keep the one Sensors tab with cards, sensors and coverage.
- **Pairing is deliberate** (Jeff): "Pair target pods" on the controller's Station tab writes `pair_mode` through the config path (`services/unitConfig`), so the page shows what the controller actually holds and a controller that reconnects gets a pending change again. It stays on until someone turns it off; no time limit. While on, the page shows a large PAIRING MODE banner, the controller's LEDs turn blue (firmware) and the kiosk will show PAIRING MODE (phase 4). A target pod sends pairing requests only while its button is held.
- **Placement follows the controller that paired it** (`services/stations.placeFromFrame`, from ingest): a target pod's frame through a controller that REPORTS pairing on creates its placement in the controller's location with `devices.controller_id` set (named "Impact target 5678" from the MAC), or moves an existing placement to this controller and location, history and all, with audit rows and a `pod_paired` or `pod_moved` event. While pairing is off, an unknown pod is only recorded as heard, so a pod deleted in the app does not come back just because it is still paired on the radio (pairing it again creates a new placement), and a pod heard by a neighbouring controller stays where it is.
- **At most one controller per location may be pairing** (Jeff): turning pairing on, from the button or the Config tab, is refused while another station type at the location reports it on or has it pending, and the page names that controller with a link. Two controllers pairing in radio range could both take the same pod.
- **Live page:** the station panel (banner, button, roster) refreshes on the same `config` socket notice the Config tab uses; pairing and moving a pod send it for the controllers involved. It fetches `GET /devices/<uid>/station` and swaps the parts marked `data-part`, so the table tools stay. A target pod's page shows which controller it is paired with. Events: `pairing_on`, `pairing_off`, `pod_paired`, `pod_moved`.
